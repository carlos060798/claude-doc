Flujo 01

🆕 Onboarding a un repo legacy de 5 años

Situación: Te incorporas a un equipo. El repo tiene 200 archivos, sin README útil, mezcla de JS y TS, y nadie tiene tiempo de explicártelo.

1
Mapa inicial del repo 
> Eres un senior engineer haciendo onboarding. Sin leer nada en detalle:
  1. Lista los directorios principales con `ls` y describe el propósito de cada uno
  2. Lee @README.md y @package.json
  3. Identifica el stack técnico, scripts npm relevantes y entry points
  4. Devuélvelo como un mapa mental en Markdown
💡 No le pidas leer todo al principio — hace consumo brutal de tokens.
2
Generar CLAUDE.md desde el código real 
> Ejecuta /init para generar un CLAUDE.md base.
  Después léelo y añade:
  - Convenciones detectadas (nombres de archivos, imports, tests)
  - Comandos npm más usados (analiza scripts en package.json)
  - Áreas peligrosas (TODOs, FIXMEs, código sin tests)
  - 3 archivos clave para entender el dominio
💡 El CLAUDE.md generado se queda en el repo y acelera todas tus sesiones futuras.
3
Trazar un flujo crítico 
> Traza el flujo completo de un login desde @src/api/auth/login.ts.
  Muéstrame: archivos involucrados, llamadas a DB, validaciones, dónde se firma
  el JWT, dónde se guarda la session. Dame un diagrama ASCII.
💡 Pídele un flujo concreto, no "explícame todo el sistema". Mucho más útil.
4
Guardar aprendizajes en memoria 
> /memory add "Auth: JWT firmado en src/api/auth/jwt.ts.
  Sessions en Redis (TTL 24h). Refresh tokens en src/api/auth/refresh.ts.
  Validación con Zod en src/shared/schemas/."
💡 Esta memoria sobrevive al cierre de sesión y futuras Claude sessions la usan.
⚠ Errores comunes:
  • Pedir "léete todo el repo" — saturas el contexto sin sacar valor
  • No actualizar CLAUDE.md después del onboarding — pierdes el aprendizaje
  • Mezclar onboarding con tareas reales — cada cosa en su sesión
Flujo 02

🧪 Añadir una feature con TDD

Situación: Te asignan implementar "rate limiting por usuario" en un endpoint. Tu equipo exige tests primero, cobertura ≥85%.

1
Diseño antes de tocar código 
> Lee @src/api/middleware/ y @CLAUDE.md.
  Diseña (sin implementar) un middleware de rate-limiting:
  - Por user.id, no por IP (evita afectar usuarios detrás de NAT)
  - 100 req/min por defecto, configurable
  - Storage en Redis (ya lo usamos)
  - Devuelve 429 con header Retry-After

  Dame: estructura del archivo, interfaces TS, casos de test a cubrir.
  NO escribas código todavía.
💡 Separar diseño de implementación produce mejores resultados.
2
Tests primero (rojos) 
> Escribe los tests Vitest para el middleware en
  @src/api/middleware/rate-limit.test.ts.
  Cubre los casos que listaste: happy path, límite alcanzado,
  reset de ventana, usuarios distintos no se afectan, Redis caído (fallback).
  Mockea Redis con @testing-library/redis-mock.

  Los tests DEBEN fallar (rojos) — el archivo de impl aún no existe.
3
Implementar hasta verde 
> Ahora implementa @src/api/middleware/rate-limit.ts
  para que pasen TODOS los tests. Sigue el diseño que definimos.
  Después de cada cambio, corre `npm test rate-limit` y muéstrame el output.
💡 Pídele que ejecute los tests él mismo — atrapa errores antes que tú.
4
Refactor con tests verdes 
> Con los tests pasando, refactoriza el middleware:
  - Extrae constantes mágicas a un objeto config
  - Mejora nombres de variables si encuentras alguno poco claro
  - Verifica que TODOS los tests sigan en verde después del refactor
5
PR con contexto 
> Crea un commit con mensaje descriptivo siguiendo Conventional Commits.
  Después abre un PR con `gh pr create` cuyo body explique:
  - Por qué hacemos rate-limiting por user.id (no por IP)
  - Cómo se configura el límite por endpoint
  - Plan de rollout: feature flag inicialmente
⚠ Errores comunes:
  • Saltar el paso de diseño — Claude implementa algo que no encaja con el resto
  • No pedir que ejecute los tests — quedan errores ocultos hasta CI
  • PR sin contexto del "por qué" — el reviewer no puede evaluar la decisión
Flujo 03

🐛 Debugging de bug intermitente en producción

Situación: Sentry reporta RangeError: Invalid time value con 47 ocurrencias en 24h, pero no se reproduce localmente.

1
Investigación con stack trace real 
> Tengo este error de Sentry:

  RangeError: Invalid time value
    at Date.toISOString (<anonymous>)
    at formatTimestamp (src/lib/dates/format.ts:42)
    at processOrder (src/features/checkout/process.ts:118)

  Lee @src/lib/dates/format.ts y @src/features/checkout/process.ts.
  Identifica QUÉ inputs podrían producir un Date inválido en formatTimestamp.
  Dame hipótesis ordenadas por probabilidad, no implementes nada.
💡 Pega el stack completo. El número de línea es oro puro.
2
Test que reproduce el bug 
> Antes de arreglarlo, escribe un test en
  @src/lib/dates/format.test.ts que reproduzca el bug con cada hipótesis.
  El test DEBE fallar ahora (demuestra que el bug existe).
💡 Test que reproduce ANTES del fix evita "lo arreglé pero no estoy seguro".
3
Fix defensivo + observabilidad 
> Arregla formatTimestamp con:
  1. Validación al entrar (Date inválido → throw con contexto)
  2. Logger.warn con el input original cuando se detecta inválido
  3. Si el caller puede recuperarse, devolver fallback documentado

  Después corre el test que escribimos: debe pasar a verde.
4
Buscar otros call sites vulnerables 
> Con grep, encuentra todos los lugares que llaman a formatTimestamp.
  Para cada uno: ¿de dónde viene el Date? ¿podría ser inválido?
  Si encuentras otros riesgos, lista las correcciones (no implementes aún).
⚠ Errores comunes:
  • Arreglar sin reproducir — un fix sin test es una hipótesis sin verificar
  • Suprimir el error con try/catch silencioso — solo lo escondes
  • No buscar otros call sites — el bug puede estar en más lugares
Flujo 04

🔄 Migrar de Express a Fastify (sin downtime)

Situación: 38 endpoints en Express. Migrar a Fastify por performance, pero sin parar producción ni romper clientes.

1
Inventario y plan por fases 
> Lista todos los endpoints (rutas + métodos) en @src/routes/.
  Agrúpalos por dominio (auth, users, payments, etc).
  Diseña un plan de migración por fases:
  - Fase A: endpoints sin estado/internos
  - Fase B: endpoints CRUD simples
  - Fase C: endpoints críticos (payments, auth)
  Para cada fase: criterios de éxito y plan de rollback.
2
Suite de tests de contrato 
> Antes de migrar nada, crea tests de contrato (input → output)
  para los 5 endpoints más críticos. Tests independientes del framework
  (usan supertest contra HTTP). Estos tests deben pasar tanto con Express
  como con Fastify después.
💡 Tests de contrato son tu red de seguridad durante la migración.
3
Migración endpoint por endpoint 
> Migra @src/routes/health.ts (el más simple) a Fastify.
  Mantén la firma HTTP idéntica. Corre los tests de contrato.
  Si pasan: commit. Si no: explícame por qué y propon una corrección.

  Después seguimos con el siguiente endpoint.
💡 Un endpoint = un commit = un PR. Reviews y rollbacks fáciles.
4
Compactar antes de seguir 
> /compact mantén el plan de migración (5 fases),
  los endpoints ya migrados (health, status, version) y la suite
  de tests de contrato. Descarta los logs de errores resueltos
  y las exploraciones iniciales.
⚠ Errores comunes:
  • Migrar todo en un solo PR — review imposible y rollback nuclear
  • Sin tests de contrato — descubres regresiones en producción
  • Cambiar el contrato HTTP "de paso" — rompes clientes que no controlas
Flujo 05

👀 Code review profundo asistido

Situación: Te asignan revisar un PR de 800 líneas en 30 minutos. Tienes que dar feedback útil sin perderte detalles importantes.

1
Resumen ejecutivo del PR 
> Lee el diff actual con `git diff main...HEAD`.
  Dame un resumen ejecutivo en 5 puntos:
  - ¿Qué problema resuelve?
  - ¿Qué archivos toca y por qué?
  - ¿Hay cambios estructurales (nuevos módulos, refactors grandes)?
  - ¿Hay tests añadidos? ¿Qué cubren?
  - ¿Qué NO hace este PR (scope explícito)?
💡 El resumen te orienta antes de bucear en líneas concretas.
2
Revisión por checklist 
> Ejecuta /code-review (nuestro Skill).
  Quiero output organizado por prioridad:
  🔴 Bloqueantes — bugs, seguridad, romper compat
  🟡 Sugerencias — mejoras de diseño, naming
  🟢 Nits — typos, espaciado, comentarios

  Para cada hallazgo: archivo:línea + por qué + fix sugerido.
3
Verificación cruzada 
> Para cada hallazgo bloqueante, dame el código exacto que lo
  causaría a fallar. Si no puedes producir un caso concreto que falla,
  reclasifícalo a "sugerencia".
💡 Esto evita falsos positivos — bloquea solo lo que realmente bloquea.
⚠ Errores comunes:
  • Aceptar todo el feedback de Claude sin verificar — incluye falsos positivos
  • Bloquear nits — frustra al autor y desincentiva PRs pequeños
  • No pedir resumen ejecutivo — te pierdes en líneas sin contexto
Flujo 06

📚 Generar documentación OpenAPI desde el código

Situación: Tu API tiene 60 endpoints. Necesitas un OpenAPI 3.1 actualizado para que el equipo de mobile/frontend genere clientes tipados.

1
Inventario de endpoints 
> Encuentra todos los endpoints en @src/routes/ y @src/controllers/.
  Para cada uno extrae:
  - Método y ruta
  - Schema de request (path/query/body) — busca Zod schemas o tipos TS
  - Schema de response (success y errores)
  - Tag de dominio (auth, users, payments…)

  Devuélvelo como tabla Markdown.
2
Generar OpenAPI YAML 
> Con esa información, genera @docs/openapi.yaml en formato OpenAPI 3.1.
  Reglas:
  - Schemas reusables en components/schemas
  - Errores documentados (400, 401, 403, 404, 500)
  - Ejemplos por endpoint (mínimo 1)
  - Servers: dev/staging/prod con URLs reales de @CLAUDE.md
3
Validar el OpenAPI 
> Corre `npx @apidevtools/swagger-cli validate docs/openapi.yaml`.
  Si hay errores, corrígelos. Si todo está bien, instala
  @scalar/api-reference y genera una preview HTML del docs.
4
Hook para mantener actualizado 
> Crea un hook PostToolUse en @.claude/settings.json:
  cuando se modifique un archivo en src/routes/ o src/controllers/,
  ejecutar `npm run docs:generate` que regenera el OpenAPI parcialmente.
  Así nunca queda desactualizado.
💡 Hooks son tu mejor defensa contra docs obsoletas.
Flujo 07

⚡ Investigar un cuello de botella de performance

Situación: Tu endpoint GET /api/dashboard tarda 4.2s en p95. Los usuarios se quejan. Tienes que bajar a <500ms.

1
Trazar la llamada completa 
> Lee @src/api/dashboard.ts. Traza la ejecución completa:
  qué queries hace, en qué orden, qué se computa en memoria.
  Identifica candidatos a cuello de botella (N+1, queries sin índice,
  loops anidados, llamadas síncronas a servicios externos).

  Dame un ranking de hipótesis ordenado por probabilidad.
2
Medir antes de optimizar 
> Añade timings con console.time/timeEnd en cada sección sospechosa.
  Corre el endpoint con un payload realista (10 items en dashboard).
  Pega los timings de vuelta y dame el análisis.
💡 Optimizar sin medir = adivinar. Mide siempre primero.
3
Aplicar fix con benchmark 
> Aplica la optimización al cuello de botella #1 (la query N+1).
  Después corre los timings de nuevo y compara con el baseline.
  Si la mejora es <30%, descártala y prueba otra hipótesis.
4
Test de regresión de performance 
> Añade un test que falle si el endpoint tarda >800ms con el dataset
  de prueba estándar. Usa vitest con timeout custom. Esto previene
  regresiones de performance en futuros cambios.
Flujo 08

🛡️ Auditoría de seguridad pre-deploy

Situación: Vas a hacer deploy a producción con datos reales por primera vez. Necesitas asegurar que no hay vulnerabilidades obvias.

1
Skill de auditoría completa 
> Ejecuta /security-audit a nivel de proyecto.
  Quiero hallazgos categorizados: SQLi, XSS, secretos, CORS,
  validación de input, manejo de errores que filtra info.

  Para cada uno: archivo:línea + severidad + fix exacto.
2
Verificar dependencias 
> Ejecuta `npm audit --audit-level high`.
  Para cada CVE crítico:
  - Lee qué hace la dependencia en nuestro código
  - Decide: ¿afecta nuestro caso de uso?
  - Si afecta: actualiza o reemplaza
  - Si no afecta: documenta el por qué en .audit-exceptions.md
3
Endurecer la configuración del agente 
> Revisa @.claude/settings.json y @.claudeignore.
  Verifica que la lista deny incluye:
  - .env, .env.* y todos los archivos con secretos
  - Comandos peligrosos (curl|sh, rm -rf /, eval)
  - Archivos de producción (production.config.*)
  Y que .claudeignore excluye node_modules, dist, backups y datos PII.
Flujo 09

🧹 Refactor agresivo con red de seguridad

Situación: Una función God de 600 líneas controla todo el checkout. Quieres dividirla sin romper nada — y tienes 0 tests sobre ella.

1
Tests de caracterización primero 
> Lee @src/checkout/process.ts (la función God).
  Identifica TODOS los outputs observables: returns, side effects (DB writes,
  emails, eventos), errores que lanza.

  Genera tests de caracterización: capturan el comportamiento ACTUAL,
  no el ideal. Estos tests son tu red — si pasan después del refactor,
  no rompiste nada externo.
💡 No "tests para verificar lo correcto" — "tests para detectar cambios".
2
Identificar responsabilidades 
> En la función God, identifica las "fases" lógicas
  (validación, cálculo de precio, charge al pago, persistencia, notificación).
  Por cada fase: qué inputs usa, qué outputs produce, dependencias externas.

  Propon una división en módulos sin implementar nada todavía.
3
Refactor por fases con commits pequeños 
> Extrae SOLO la fase de validación a un módulo nuevo.
  La función original sigue funcionando, solo delega esa parte.
  Corre los tests de caracterización: deben seguir verdes.

  Commit. Después seguimos con la fase de cálculo de precio.
Flujo 10

🤖 Automatizar tu rutina de developer

Situación: Cada mañana repites: pull, npm install, leer Slack de tu equipo, revisar PRs asignados, decidir en qué trabajar. 30 min perdidos.

1
Skill de "buenos días" 
> Crea ~/.claude/skills/morning-brief/SKILL.md que:
  - Hace `git pull` en el repo actual
  - Ejecuta `gh pr list --assignee @me` para ver PRs míos
  - Ejecuta `gh issue list --assignee @me --state open`
  - Lee mi memoria con /memory para recordar en qué iba ayer
  - Me da un brief de 5 líneas con: PRs pendientes, issues asignados,
    en qué quedé ayer, sugerencia de en qué empezar hoy.
2
Hook para "fin de día" 
> Configura un hook SessionEnd en ~/.claude/settings.json
  que ejecute /curso-checkpoint y guarde un resumen de la sesión
  en ~/.claude/sessions/$(date +%Y-%m-%d).md.

  Mañana cuando vuelva, /morning-brief lo lee como contexto.
3
MCPs de productividad 
> Conecta como user-scope (disponible en todos mis proyectos):
  - GitHub (PRs, issues, notifications)
  - Linear o Jira (tickets asignados)
  - Slack (mentions y DMs sin leer)

  Después /morning-brief tendrá acceso real a todo eso, no solo CLI.
💡 user-scope vs project-scope: para herramientas tuyas usa user.

Nivel 2 Avanzado: MCP & Tokens

Conecta Claude Code a herramientas externas vía Model Context Protocol y aprende a gestionar tu ventana de contexto como un profesional.

2.1 — Model Context Protocol (MCP)

MCP es un estándar abierto creado por Anthropic que permite a Claude Code comunicarse con servicios externos (GitHub, Postgres, Slack, navegadores) vía servidores que exponen herramientas, recursos y prompts. Soporta tres transportes: stdio (local, baja latencia), SSE (remoto streaming) y HTTP. 

# Exporta tu token como variable de entorno (NO lo escribas en el JSON)
export GITHUB_TOKEN="ghp_tu_token_aqui"

# Registra el servidor MCP de GitHub (transporte stdio por defecto)
claude mcp add github -e GITHUB_TOKEN -- npx -y @modelcontextprotocol/server-github

# Verifica que esté conectado
claude mcp list
# Salida esperada:  github: connected (stdio)
# Servidor remoto SSE
claude mcp add --transport sse my-remote https://mi-servidor.com/mcp/sse

# Servidor remoto HTTP con headers de auth
claude mcp add --transport http composio-server "https://mcp.composio.dev/..." \
  --headers "X-API-Key:TU_API_KEY"

3.2 — Crear tu primera Skill: /security-audit

---
name: security-audit
description: Audita el código en busca de vulnerabilidades comunes
  (SQLi, XSS, secretos expuestos, configuraciones inseguras). Úsalo
  cuando el usuario mencione seguridad, hardening o revisión de
  vulnerabilidades.
allowed-tools: Read, Grep, Glob, Bash(git diff:*)
model: claude-opus-4-7
---

# Auditoría de Seguridad

Analiza el código del proyecto buscando:

1. **Inyección SQL** — queries construidas por concatenación
2. **XSS** — output sin escapar en plantillas / DOM
3. **Secretos expuestos** — keys, tokens, contraseñas en código
4. **Configuraciones inseguras** — CORS abierto, debug=true, etc.
5. **Dependencias vulnerables** — revisa package.json / requirements

Para cada hallazgo, devuelve:
- Archivo y línea exacta
- Severidad (crítica / alta / media / baja)
- Código actual + parche recomendado
- Referencia OWASP cuando aplique

Una vez guardado, la Skill está disponible inmediatamente. Invócala con /security-audit o deja que Claude la dispare automáticamente cuando detecte intención coincidente con el campo description.

# Refactorización en paralelo

Con la herramienta Task, crea dos sub-agentes:


Seguridad & Hardening

Trabajar con un agente que tiene acceso a tu sistema de archivos requiere una postura defensiva. Estas son las prácticas mínimas que un perfil senior debe aplicar antes de poner Claude Code en un entorno con datos reales.

🛡 1. Prevenir fuga de archivos .env y secretos

El bloqueo se hace a nivel de permisos del agente, no solo del .gitignore. La directiva deny impide explícitamente que Claude lea o escriba sobre rutas sensibles, incluso si tú se lo pides. 

{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./**/secrets/**)",
      "Read(./**/*.pem)",
      "Read(./**/*.key)",
      "Read(./id_rsa)",
      "Write(./production.config.*)",
      "Bash(curl * | sh)",
      "Bash(rm -rf /*)"
    ]
  }
}

🛡 3. MCP: tokens vía variables de entorno

Nunca escribas tokens directamente en .mcp.json. Usa la flag -e al registrar el servidor — el token vive en tu shell, no en archivos versionados. 

# ❌ MAL: token literal en JSON (acaba en git)

🛡 4. Mitigar sesgos de seguridad en código generado

Los LLMs tienden a generar patrones inseguros si no se les corrige (ej. queries por concatenación, validación cliente-only, CORS abierto). Estrategias:

  • CLAUDE.md con reglas explícitas: «Toda query SQL DEBE usar parámetros preparados. Nunca SELECT * FROM x WHERE id = ${id}.»
  • Hook PostToolUse que ejecute un linter de seguridad (semgrep, bandit) tras cada Write.
  • Skill /security-audit obligatoria antes de mergear.
  • Principio de mínimo privilegio en allowedTools: no concedas Bash(*); lista comandos uno a uno.

🛡 5. Auditoría de servidores MCP de terceros

⚠ Crítico: Un servidor MCP es código que se ejecuta con tus permisos. Antes de instalar uno de la comunidad: revisa el repositorio, fija la versión exacta (@1.2.3, nunca @latest), y prefiere tokens de solo lectura cuando el caso de uso lo permita.

SDK-2 — Agente básico con herramientas

Un agente que puede leer archivos y ejecutar comandos bash:

import Anthropic from '@anthropic-ai/sdk';
import { execSync } from 'child_process';
import { readFileSync } from 'fs';

const client = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });

const tools: Anthropic.Tool[] = [
  {
    name: 'read_file',
    description: 'Lee el contenido de un archivo del sistema',
    input_schema: {
      type: 'object',
      properties: {
        path: { type: 'string', description: 'Ruta al archivo' }
      },
      required: ['path']
    }
  },
  {
    name: 'run_bash',
    description: 'Ejecuta un comando bash y devuelve stdout',
    input_schema: {
      type: 'object',
      properties: {
        command: { type: 'string', description: 'Comando a ejecutar' }
      },
      required: ['command']
    }
  }
];

async function runAgent(userMessage: string) {
  const messages: Anthropic.MessageParam[] = [
    { role: 'user', content: userMessage }
  ];

  while (true) {
    const response = await client.messages.create({
      model: 'claude-sonnet-4-6',
      max_tokens: 4096,
      tools,
      messages
    });

    // Añadir respuesta al historial
    messages.push({ role: 'assistant', content: response.content });

    if (response.stop_reason === 'end_turn') break;

    if (response.stop_reason === 'tool_use') {
      const toolResults: Anthropic.ToolResultBlockParam[] = [];

      for (const block of response.content) {
        if (block.type !== 'tool_use') continue;

        let result = '';
        if (block.name === 'read_file') {
          result = readFileSync((block.input as any).path, 'utf8');
        } else if (block.name === 'run_bash') {
          result = execSync((block.input as any).command, { encoding: 'utf8' });
        }

        toolResults.push({
          type: 'tool_result',
          tool_use_id: block.id,
          content: result
        });
      }

      messages.push({ role: 'user', content: toolResults });
    }
  }

  // Extraer texto final
  const lastMsg = messages[messages.length - 1];
  const content = Array.isArray(lastMsg.content) ? lastMsg.content : [];
  return content.find(b => b.type === 'text')?.text ?? '';
}

// Uso
const result = await runAgent(
  'Lee @src/index.ts y dame un resumen de la arquitectura'
);
console.log(result);

SDK-5 — Prompt caching (reducción de costos)

El prompt caching reduce costos hasta un 90% y latencia hasta un 85% cuando reutilizas contexto largo (documentos, instrucciones de sistema). 

import Anthropic from '@anthropic-ai/sdk';
import { readFileSync } from 'fs';

const client = new Anthropic();

// Cargar documento grande una vez

async function queryWithCache(question: string) {
  const response = await client.messages.create({
    model: 'claude-sonnet-4-6',
    max_tokens: 1024,
    system: [
      {
        type: 'text',
        text: 'Eres un asistente experto en esta documentación.',
        // ↓ Marcar para cachear — Anthropic almacena hasta 5 min
        cache_control: { type: 'ephemeral' }
      },
      {
        type: 'text',
        text: largeDoc,
        cache_control: { type: 'ephemeral' }  // cachea el doc completo
      }
    ],
    messages: [{ role: 'user', content: question }]
  });

  const usage = response.usage as any;
  console.log(`Cache hit: ${usage.cache_read_input_tokens ?? 0} tokens`);
  console.log(`Cache write: ${usage.cache_creation_input_tokens ?? 0} tokens`);

  return response.content[0].type === 'text' ? response.content[0].text : '';
}

API-8 — Manejo de errores y retry

import Anthropic from '@anthropic-ai/sdk';

// El SDK tiene retry automático por defecto (2 reintentos)
const client = new Anthropic({
  maxRetries: 3,         // Reintentos para 429/529
  timeout: 30_000,       // Timeout por request (ms)
});

async function safeRequest(prompt: string) {
  try {
    const response = await client.messages.create({
      model: 'claude-sonnet-4-6',
      max_tokens: 1024,
      messages: [{ role: 'user', content: prompt }]
    });
    return { ok: true, data: response };

  } catch (err) {
    if (err instanceof Anthropic.APIError) {
      switch (err.status) {
        case 400: return { ok: false, error: `Bad Request: ${err.message}` };
        case 401: return { ok: false, error: 'API Key inválida o expirada' };
        case 403: return { ok: false, error: 'Sin permisos para este recurso' };
        case 429: return { ok: false, error: 'Rate limit — reduce la frecuencia' };
        case 529: return { ok: false, error: 'API sobrecargada — reintenta más tarde' };
        default:  return { ok: false, error: `Error ${err.status}: ${err.message}` };
      }
    }
    throw err;   // Re-lanzar errores inesperados
  }
}

               2. XSS (output sin escapar)

               4. CORS inseguro
               5. Ejecución de comandos sin sanitizar
               Si encuentras algo crítico devuelve JSON: {\"critical\": true, \"issues\": [...]}
               Si está limpio devuelve: {\"critical\": false}" \
              < "$FILE" --output-format json --dangerously-skip-permissions)

            CRITICAL=$(echo $RESULT | jq -r '.critical // false')
            if [ "$CRITICAL" = "true" ]; then
              echo "❌ CRÍTICO en $FILE:"
              echo $RESULT | jq -r '.issues[]'
              FOUND_ISSUES=true
            else
              echo "✅ Limpio: $FILE"
            fi
          done

          if [ "$FOUND_ISSUES" = "true" ]; then
            exit 1
          fi

CI-5 — Script de migración asistida

#!/bin/bash
# Migración asistida de JS → TS con Claude Code
# Uso: ./scripts/migrate-with-claude.sh src/utils/

set -e
TARGET_DIR=${1:-src/}
CLAUDE_OPTS="--dangerously-skip-permissions"

echo "🔄 Iniciando migración JS→TS en $TARGET_DIR"

# Encontrar todos los .js (excluyendo node_modules y config)
JS_FILES=$(find "$TARGET_DIR" -name "*.js" \
  -not -path "*/node_modules/*" \
  -not -name "*.config.js" \
  -not -name "*.test.js")

TOTAL=$(echo "$JS_FILES" | wc -l)
COUNT=0

for FILE in $JS_FILES; do
  COUNT=$((COUNT + 1))
  echo "[$COUNT/$TOTAL] Migrando $FILE..."

  TS_FILE="${FILE%.js}.ts"

  # Claude migra el archivo con tipos estrictos
  claude -p \
    "Migra este archivo JavaScript a TypeScript estricto.
     - Infiere tipos desde el uso (no uses 'any')
     - Añade interfaces para objetos complejos
     - Preserva toda la lógica de negocio sin cambios
     - Actualiza imports para usar extensión .ts
     - NO cambies el comportamiento observable
     Devuelve SOLO el código TypeScript, sin explicaciones ni backticks." \
    < "$FILE" $CLAUDE_OPTS > "$TS_FILE"

  # Verificar que compila
  if npx tsc --noEmit "$TS_FILE" 2>/dev/null; then
    echo "  ✅ $TS_FILE compila correctamente"
    rm "$FILE"  # Eliminar original JS
  else
    echo "  ⚠️  $TS_FILE tiene errores de tipo — revisar manualmente"
    rm "$TS_FILE"  # Mantener original JS si hay errores
  fi

  # Rate limiting: no sobresaturar la API
  sleep 0.5
done

echo "✅ Migración completada: $COUNT archivos procesados"
echo "💡 Ejecuta 'npm run typecheck' para verificar el proyecto completo"

BP-2 — Gestión eficiente de tokens

01

Usa @ selectivamente

No menciones archivos completos cuando basta con una función. @src/utils.ts:42-80 (líneas específicas) consume mucho menos que el archivo entero.

02

Compacta antes del 75%

Con instrucciones explícitas: /compact preserva X, descarta Y. Compactar a ciegas puede perder contexto crítico.

03

Separa tareas por sesión

Una sesión = un objetivo. Mezclar refactor + review + debug en la misma sesión infla el contexto innecesariamente.

04

CLAUDE.md conciso

Cada byte del CLAUDE.md se carga en cada sesión. Mantén la información densa y elimina lo que ya no aplica al proyecto actual.

05

Modelo correcto para la tarea

Haiku para clasificación/extracción rápida. Sonnet para el 80% del trabajo. Opus solo para análisis críticos que justifican el costo.

06

Limita MCP servers

Cada servidor MCP conectado añade tokens al contexto. Solo conecta los servidores que usas activamente en la sesión actual.

¿Qué es Claude Code?

Claude Code es una forma completamente diferente de trabajar. En lugar de escribir todo manualmente, le cuentas qué quieres y Claude lo entiende de inmediato, considerando todo tu proyecto.

3 Razones clave:

  • 🎯 Entiende tu contexto: Conoce tu proyecto completo, no solo una función.
  • 🔄 Aprende tu estilo: Recuerda tus decisiones y preferencias entre sesiones.

Glosario: Términos que necesitas conocer

Explicaciones simples de términos técnicos, con analogías y ejemplos reales.

Contexto

Definición simple: Información que Claude Code recuerda durante tu sesión.

Analogía: Es como tu conversación con un amigo — mientras más le dices, mejor te entiende.

Ejemplo: Si subes un archivo de datos, Claude lo recuerda para los siguientes comandos. Si mencionas que eres un PM, recordará eso.

Token

Definición simple: Una pequeña unidad de texto, aproximadamente una palabra.

Analogía: Son como monedas del lenguaje. Cada pregunta y respuesta gasta cierta cantidad de tokens.

Ejemplo: Una pregunta simple = ~50 tokens. Un documento de 5 páginas = ~2000 tokens.

MCP (Model Context Protocol)

Definición simple: Conexiones a herramientas especiales que Claude Code puede usar.

Analogía: Como enchufes especializados. Puedes conectar GitHub, Slack, Jira, etc., y Claude accede a ellos automáticamente.

Ejemplo: Con MCP de GitHub, Claude puede leer tus commits sin que le copies manualmente el código.

Skill

Definición simple: Un comando personalizado que creas para tareas repetitivas.

Analogía: Como una receta: defines los pasos una vez y luego la reutilizas infinitas veces.

Ejemplo: Crear `/analizar-feedback` — tu Skill personalizado que procesa customer feedback automáticamente.

Memoria

Definición simple: Información que Claude Code guarda entre sesiones.

Analogía: Tu cuaderno personal: no olvida decisiones, preferencias y contexto del proyecto.

Ejemplo: Guardar "usa siempre TypeScript en este proyecto" y Claude lo recordará mañana, la próxima semana, siempre.

Comando

Definición simple: Una instrucción que empiezas con `/` o que ejecutas en la terminal.

Analogía: Como accesos rápidos o atajos: `/help` = pedir ayuda, `/clear` = empezar de cero.

Ejemplo: Escribes `/model claude-opus-4-7` para cambiar al modelo más potente.
