Comandos y Hooks

Diferencia entre comandos de usuario y disparadores automáticos en el ciclo de vida del mensaje

📖 Documentación oficial: Hooks Reference — Claude Code Docs

🎥 Video: Hooks y Automatización en Claude Code

Fundamentos

¿Qué es un Comando?

Un comando es una instrucción que el usuario inicia explícitamente, comenzando con /. Ejemplos:

bash — Comandos de usuario 
/help              # Listar todos los comandos disponibles
/model             # Ver/cambiar modelo actual
/context           # Ver uso de contexto
/clear             # Limpiar historial
/memory            # Gestionar memoria persistente
/config            # Ver/modificar configuración
/mcp               # Listar servidores MCP conectados

Características:

  • Iniciados por el usuario explícitamente
  • Se ejecutan 1 sola vez cuando se invoca
  • Devuelven respuesta inmediata
  • No afectan comandos futuros (a menos que cambien estado)

¿Qué es un Hook?

Un hook es un disparador automático que se ejecuta automáticamente en ciertos momentos del ciclo de vida. No requiere invocación del usuario.

text — Tipos de Hooks 
PreToolUse      → Justo antes de usar una herramienta
PostToolUse     → Después de que una herramienta devuelve resultado
PostToolError   → Si una herramienta falla
OnCompilation   → Cuando compila un cambio de código
OnModeChange    → Cuando cambia el modelo activo
OnSessionStart  → Al iniciar una nueva sesión
OnSessionEnd    → Al finalizar la sesión

Características:

  • Disparados automáticamente por eventos
  • Se ejecutan cada vez que ocurre el evento
  • Pueden transformar datos antes/después de operaciones
  • No requieren intervención del usuario

Diferencia Clave

Aspecto Comando Hook
Iniciación Manual (usuario escribe /comando) Automática (evento)
Frecuencia Cuando usuario lo invoca Cada vez que ocurre el evento
Propósito Realizar acción puntual Automatizar procesos repetitivos
Ejemplo /help → muestra comandos PostToolUse → formatea output

Caso Práctico 1: Bloquear comandos destructivos (PreToolUse)

json — .claude/settings.json 
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(rm *)",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/block-destructive.sh"
          }
        ]
      }
    ]
  }
}
bash — .claude/hooks/block-destructive.sh 
#!/bin/bash
set -e
COMMAND=$(jq -r '.tool_input.command')

# Bloquear comandos destructivos
if echo "$COMMAND" | grep -E '^rm -rf|^:(){:|:|&&&' > /dev/null; then
  jq -n '{
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",
      permissionDecisionReason: "Comando destructivo bloqueado por seguridad"
    }
  }'
  exit 0
fi

exit 0  # Permitir todos los demás

json — Hook auto-format 
{

    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/auto-format.sh"
          }
        ]
      }
    ]
  }
}
bash — .claude/hooks/auto-format.sh 
#!/bin/bash
FILE=$(jq -r '.tool_input.file_path')

case "$FILE" in
  *.py)  python -m black "$FILE" --quiet ;;
  *.js|*.ts|*.jsx|*.tsx) npx prettier "$FILE" --write ;;
  *.go)  gofmt -w "$FILE" ;;
  *.json) python -m json.tool "$FILE" > /tmp/fmt && mv /tmp/fmt "$FILE" ;;
esac

exit 0

bash — validate-prompt.sh 
#!/bin/bash
PROMPT=$(jq -r '.prompt')

# Bloquear prompts con datos sensibles
if echo "$PROMPT" | grep -iE 'password|secret|api.?key|token' > /dev/null; then
  jq -n '{
    decision: "block",
    reason: "Prompt contiene información sensible. Por favor no incluyas credenciales."
  }'
  exit 0
fi

# Agregar contexto del ambiente actual
jq -n '{
  hookSpecificOutput: {
    hookEventName: "UserPromptSubmit",
    additionalContext: "Ambiente: production | Fecha: '"$(date)"'"
  }
}'
exit 0

SessionStart: Cargar Contexto Automático

json — Cargar contexto al iniciar 
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/load-context.sh"
          }
        ]
      }
    ]
  }
}
bash — load-context.sh 
#!/bin/bash
# Exportar variables al ambiente de Claude
if [ -n "$CLAUDE_ENV_FILE" ]; then
  echo "export NODE_ENV=production" >> "$CLAUDE_ENV_FILE"
  echo "export APP_VERSION=$(cat package.json | jq -r .version)" >> "$CLAUDE_ENV_FILE"
fi

# Proveer contexto adicional a Claude
BRANCH=$(git branch --show-current 2>/dev/null || echo "unknown")
LAST_COMMIT=$(git log -1 --format="%h %s" 2>/dev/null || echo "N/A")
OPEN_PRS=$(gh pr list --state open --json number --jq length 2>/dev/null || echo "N/A")

jq -n --arg branch "$BRANCH" \
      --arg commit "$LAST_COMMIT" \
      --arg prs "$OPEN_PRS" '{
  hookSpecificOutput: {
    hookEventName: "SessionStart",
    additionalContext: "Branch: \($branch) | Último commit: \($commit) | PRs abiertos: \($prs)"
  }
}'
exit 0

Extended Thinking — Razonamiento Profundo

Activar modo de pensamiento extendido para problemas complejos que requieren cadenas de razonamiento

📚 Referencia oficial: Extended Thinking API
Fundamentos

¿Qué es Extended Thinking?

Extended Thinking es un modo donde Claude dedica tokens invisibles al usuario a razonar internamente antes de responder. La cadena de pensamiento no se muestra, pero mejora significativamente la calidad de respuestas en problemas complejos.

text — Sin vs Con Extended Thinking 
Sin Extended Thinking (respuesta rápida):
- Respuesta inmediata
- Buena para tareas simples (resúmenes, redacción)
- ~100-500 tokens
- Costo: bajo

Con Extended Thinking (respuesta reflexionada):
- Claude dedica 5-10s a razonar internamente
- Excelente para: arquitectura, debugging difícil, matemática, lógica
- ~1000-8000 tokens de pensamiento (invisibles)
- Costo: ~3x más (pero valor 10x mayor en casos complejos)

Cuándo Activar Extended Thinking

Tarea¿Usar?Razón
Escribir una carta❌ NoTareas simples, respuesta directa
Diseñar arquitectura de sistema✅ SíMúltiples trade-offs, decisiones complejas
Resumen de artículo❌ NoProcesamiento lineal, sin razonamiento
Encontrar bug en código legacy✅ SíRequiere exploración, análisis profundo
Generar tweet❌ NoCreatividad inmediata, no análisis
Estrategia de optimización✅ SíMúltiples variables, trade-offs

Usar Extended Thinking con SDK

python — Con Anthropic SDK 
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-opus-4-7",
    max_tokens=16000,  # Necesario para thinking + respuesta
    thinking={
        "type": "enabled",
        "budget_tokens": 10000  # Tokens para razonar (no es parte del output)
    },
    messages=[
        {
            "role": "user",
            "content": "Analiza este código y propón una refactorización completa"
        }
    ]
)

# Acceder al pensamiento y respuesta
for block in response.content:
    if block.type == "thinking":
        print("🧠 Cadena de pensamiento:")
        print(block.thinking)
    elif block.type == "text":
        print("📝 Respuesta final:")
        print(block.text)

# Métricas de tokens
print(f"Tokens pensamiento: {response.usage.cache_creation_input_tokens or 0}")
print(f"Tokens input: {response.usage.input_tokens}")
print(f"Tokens output: {response.usage.output_tokens}")

Estrategias de Costo-Beneficio

Extended Thinking cuesta ~3x más, pero para ciertos problemas vale 10x. Usa esta fórmula:

python — Análisis de ROI 
def should_use_extended_thinking(task_complexity, num_iterations):
    """
    task_complexity: 1-5 (1=trivial, 5=muy complejo)
    num_iterations: cuántas veces se ejecutará
    """
    # Sin thinking: 0.5 USD por 1M tokens
    # Con thinking: 1.5 USD por 1M tokens (thinking) + 0.5 (respuesta)

    cost_without = 0.5 * num_iterations  # Versión simple
    cost_with = 1.5 * num_iterations     # Versión con thinking

    # Pero si task_complexity es alto, probablemente necesites 3 iteraciones
    # sin thinking vs 1 con thinking para llegar al mismo resultado

    iterations_needed_without = 3 if task_complexity > 3 else 1
    iterations_needed_with = 1

    cost_without_realistic = 0.5 * iterations_needed_without
    cost_with_realistic = 1.5 * iterations_needed_with

    return cost_with_realistic < cost_without_realistic

# Ejemplos:
print("Debugging difícil:", should_use_extended_thinking(4, 1))  # True
print("Escribir email:", should_use_extended_thinking(1, 1))     # False

Los Sub-Agentes son agentes de IA especializados que pueden ser invocados desde Claude Code para realizar tareas específicas. Cada sub-agente tiene:

Fork: Aislamiento de Contexto

El comando /fork crea una copia del contexto actual en un sub-agente aislado — los cambios no afectan la sesión padre:

# Caso de uso: probar diferentes enfoques sin contaminar el contexto

# Si uno de los forks falla, no afecta al otro ni al principal

Resumir Sub-Agentes: SendMessage

text — Ciclo de vida de un sub-agente 
1. SPAWN (iniciar)
   Agent({ description: "...", prompt: "...", subagent_type: "code-reviewer" })
   → El agente comienza a trabajar en background

2. WORK (trabajar)
   El sub-agente ejecuta herramientas, lee archivos, genera resultados
   El agente padre continúa con otras tareas

3. COMPLETE (completar)
   El sub-agente devuelve resultado al padre via retorno del tool
   El resultado NO es visible al usuario automáticamente

4. RESUME (continuar un agente previo)
   SendMessage({ to: "agentId", content: "Continúa con X" })
   → Retoma el sub-agente con FULL contexto previo
   → CRUCIAL: No crear nuevo Agent() — eso borra el historial

  • Frontmatter (YAML) entre --- — Metadatos de configuración

# pip install mcp

from mcp.server import Server
from mcp.server.stdio import stdio_server
from mcp import types
import asyncio

server = Server("my-company-api")

@server.list_tools()
async def list_tools() -> list[types.Tool]:
    return [
        types.Tool(
            name="get_customer",
            description="Obtiene datos de un cliente por ID",
            inputSchema={
                "type": "object",
                "properties": {
                    "customer_id": {
                        "type": "string",
                        "description": "ID del cliente"
                    }
                },
                "required": ["customer_id"]
            }
        ),
        types.Tool(
            name="list_orders",
            description="Lista órdenes de un cliente",
            inputSchema={
                "type": "object",
                "properties": {
                    "customer_id": {"type": "string"},
                    "limit": {"type": "integer", "default": 10}
                },
                "required": ["customer_id"]
            }
        )
    ]

@server.call_tool()
async def call_tool(name: str, arguments: dict) -> list[types.TextContent]:
    if name == "get_customer":
        # Tu lógica aquí
        customer_id = arguments["customer_id"]
        # data = await fetch_from_api(f"/customers/{customer_id}")
        data = {"id": customer_id, "name": "John Doe", "email": "john@example.com"}
        return [types.TextContent(type="text", text=str(data))]

    elif name == "list_orders":
        customer_id = arguments["customer_id"]

        return [types.TextContent(type="text", text=str(orders))]

    raise ValueError(f"Tool desconocida: {name}")

async def main():
    async with stdio_server() as (read_stream, write_stream):
        await server.run(read_stream, write_stream, server.create_initialization_options())

if __name__ == "__main__":
    asyncio.run(main())

SDK y Prompt Caching

Estructurar mensajes para máxima eficiencia de tokens

Fundamentos

¿Qué es Prompt Caching?

Prompt Caching es una técnica donde Claude recuerda contexto (documentación, instrucciones, datos) entre múltiples mensajes sin contar tokens repetidamente.

Sin caching: Cada pregunta = leer toda la documentación nuevamente = X tokens cada vez.

Con caching: Lees documentación 1 vez, luego reutilizas = costo reducido ~90%.

Estructura de Mensajes

Un mensaje en Claude tiene 3 partes:

python — Estructura básica 
from anthropic import Anthropic

client = Anthropic()

message = client.messages.create(
    model="claude-opus-4-7",
    max_tokens=1024,
    system="Eres un asistente de Python.",  # System prompt
    messages=[
        {
            "role": "user",
            "content": "¿Cuál es la diferencia entre list y tuple?"
        }
    ]
)

print(message.content[0].text)

Partes:

  • system — Instrucciones globales (rol, restricciones)
  • messages — Historial de conversación
  • model — Qué modelo usar (Opus, Sonnet, Haiku)

Análisis de Costo: Cuándo Caching Compensa

Fórmula para decidir si usar caching:

python — Cost analysis 
def should_use_caching(
    doc_size_tokens: int,
    num_queries: int,
    avg_query_tokens: int
) -> bool:
    """
    Determina si vale la pena usar caching.

    Costo SIN caching: doc_size * num_queries
    Costo CON caching: doc_size * 1.25 (creación) + avg_query * num_queries
    """

    cost_without = doc_size_tokens * num_queries * 0.003 / 1000000
    cost_with = (doc_size_tokens * 1.25 * 0.003 / 1000000) + \
                (avg_query_tokens * num_queries * 0.0015 / 1000000)

    print(f"Sin caching: ${cost_without:.4f}")
    print(f"Con caching: ${cost_with:.4f}")
    print(f"Ahorro: ${cost_without - cost_with:.4f}")

    return cost_with < cost_without

# Ejemplo: documentación de 10K tokens, 10 queries
should_use_caching(doc_size_tokens=10000, num_queries=10, avg_query_tokens=500)
# Resultado: caching COMPENSA después de ~3 queries
