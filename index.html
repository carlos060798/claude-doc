🔄 Flujos Reales de Developer

10 escenarios completos sacados del día a día de equipos de producción. Cada flujo incluye contexto, prompts efectivos paso a paso, qué esperar, y los errores comunes a evitar.

Flujo 01

🆕 Onboarding a un repo legacy de 5 años

Situación: Te incorporas a un equipo. El repo tiene 200 archivos, sin README útil, mezcla de JS y TS, y nadie tiene tiempo de explicártelo.

1
Mapa inicial del repo 
> Eres un senior engineer haciendo onboarding. Sin leer nada en detalle:
  1. Lista los directorios principales con `ls` y describe el propósito de cada uno
  2. Lee @README.md y @package.json
  3. Identifica el stack técnico, scripts npm relevantes y entry points
  4. Devuélvelo como un mapa mental en Markdown
💡 No le pidas leer todo al principio — hace consumo brutal de tokens.
2
Generar CLAUDE.md desde el código real 
> Ejecuta /init para generar un CLAUDE.md base.
  Después léelo y añade:
  - Convenciones detectadas (nombres de archivos, imports, tests)
  - Comandos npm más usados (analiza scripts en package.json)
  - Áreas peligrosas (TODOs, FIXMEs, código sin tests)
  - 3 archivos clave para entender el dominio
💡 El CLAUDE.md generado se queda en el repo y acelera todas tus sesiones futuras.
3
Trazar un flujo crítico 
> Traza el flujo completo de un login desde @src/api/auth/login.ts.
  Muéstrame: archivos involucrados, llamadas a DB, validaciones, dónde se firma
  el JWT, dónde se guarda la session. Dame un diagrama ASCII.
💡 Pídele un flujo concreto, no "explícame todo el sistema". Mucho más útil.
4
Guardar aprendizajes en memoria 
> /memory add "Auth: JWT firmado en src/api/auth/jwt.ts.
  Sessions en Redis (TTL 24h). Refresh tokens en src/api/auth/refresh.ts.
  Validación con Zod en src/shared/schemas/."
💡 Esta memoria sobrevive al cierre de sesión y futuras Claude sessions la usan.
⚠ Errores comunes:
  • Pedir "léete todo el repo" — saturas el contexto sin sacar valor
  • No actualizar CLAUDE.md después del onboarding — pierdes el aprendizaje
  • Mezclar onboarding con tareas reales — cada cosa en su sesión
Flujo 02

🧪 Añadir una feature con TDD

Situación: Te asignan implementar "rate limiting por usuario" en un endpoint. Tu equipo exige tests primero, cobertura ≥85%.

1
Diseño antes de tocar código 
> Lee @src/api/middleware/ y @CLAUDE.md.
  Diseña (sin implementar) un middleware de rate-limiting:
  - Por user.id, no por IP (evita afectar usuarios detrás de NAT)
  - 100 req/min por defecto, configurable
  - Storage en Redis (ya lo usamos)
  - Devuelve 429 con header Retry-After

  Dame: estructura del archivo, interfaces TS, casos de test a cubrir.
  NO escribas código todavía.
💡 Separar diseño de implementación produce mejores resultados.
2
Tests primero (rojos) 
> Escribe los tests Vitest para el middleware en
  @src/api/middleware/rate-limit.test.ts.
  Cubre los casos que listaste: happy path, límite alcanzado,
  reset de ventana, usuarios distintos no se afectan, Redis caído (fallback).
  Mockea Redis con @testing-library/redis-mock.

  Los tests DEBEN fallar (rojos) — el archivo de impl aún no existe.
3
Implementar hasta verde 
> Ahora implementa @src/api/middleware/rate-limit.ts
  para que pasen TODOS los tests. Sigue el diseño que definimos.
  Después de cada cambio, corre `npm test rate-limit` y muéstrame el output.
💡 Pídele que ejecute los tests él mismo — atrapa errores antes que tú.
4
Refactor con tests verdes 
> Con los tests pasando, refactoriza el middleware:
  - Extrae constantes mágicas a un objeto config
  - Mejora nombres de variables si encuentras alguno poco claro
  - Verifica que TODOS los tests sigan en verde después del refactor
5
PR con contexto 
> Crea un commit con mensaje descriptivo siguiendo Conventional Commits.
  Después abre un PR con `gh pr create` cuyo body explique:
  - Por qué hacemos rate-limiting por user.id (no por IP)
  - Cómo se configura el límite por endpoint
  - Plan de rollout: feature flag inicialmente
⚠ Errores comunes:
  • Saltar el paso de diseño — Claude implementa algo que no encaja con el resto
  • No pedir que ejecute los tests — quedan errores ocultos hasta CI
  • PR sin contexto del "por qué" — el reviewer no puede evaluar la decisión
Flujo 03

🐛 Debugging de bug intermitente en producción

Situación: Sentry reporta RangeError: Invalid time value con 47 ocurrencias en 24h, pero no se reproduce localmente.

1
Investigación con stack trace real 
> Tengo este error de Sentry:

  RangeError: Invalid time value
    at Date.toISOString (<anonymous>)
    at formatTimestamp (src/lib/dates/format.ts:42)
    at processOrder (src/features/checkout/process.ts:118)

  Lee @src/lib/dates/format.ts y @src/features/checkout/process.ts.
  Identifica QUÉ inputs podrían producir un Date inválido en formatTimestamp.
  Dame hipótesis ordenadas por probabilidad, no implementes nada.
💡 Pega el stack completo. El número de línea es oro puro.
2
Test que reproduce el bug 
> Antes de arreglarlo, escribe un test en
  @src/lib/dates/format.test.ts que reproduzca el bug con cada hipótesis.
  El test DEBE fallar ahora (demuestra que el bug existe).
💡 Test que reproduce ANTES del fix evita "lo arreglé pero no estoy seguro".
3
Fix defensivo + observabilidad 
> Arregla formatTimestamp con:
  1. Validación al entrar (Date inválido → throw con contexto)
  2. Logger.warn con el input original cuando se detecta inválido
  3. Si el caller puede recuperarse, devolver fallback documentado

  Después corre el test que escribimos: debe pasar a verde.
4
Buscar otros call sites vulnerables 
> Con grep, encuentra todos los lugares que llaman a formatTimestamp.
  Para cada uno: ¿de dónde viene el Date? ¿podría ser inválido?
  Si encuentras otros riesgos, lista las correcciones (no implementes aún).
⚠ Errores comunes:
  • Arreglar sin reproducir — un fix sin test es una hipótesis sin verificar
  • Suprimir el error con try/catch silencioso — solo lo escondes
  • No buscar otros call sites — el bug puede estar en más lugares
Flujo 04

🔄 Migrar de Express a Fastify (sin downtime)

Situación: 38 endpoints en Express. Migrar a Fastify por performance, pero sin parar producción ni romper clientes.

1
Inventario y plan por fases 
> Lista todos los endpoints (rutas + métodos) en @src/routes/.
  Agrúpalos por dominio (auth, users, payments, etc).
  Diseña un plan de migración por fases:
  - Fase A: endpoints sin estado/internos
  - Fase B: endpoints CRUD simples
  - Fase C: endpoints críticos (payments, auth)
  Para cada fase: criterios de éxito y plan de rollback.
2
Suite de tests de contrato 
> Antes de migrar nada, crea tests de contrato (input → output)
  para los 5 endpoints más críticos. Tests independientes del framework
  (usan supertest contra HTTP). Estos tests deben pasar tanto con Express
  como con Fastify después.
💡 Tests de contrato son tu red de seguridad durante la migración.
3
Migración endpoint por endpoint 
> Migra @src/routes/health.ts (el más simple) a Fastify.
  Mantén la firma HTTP idéntica. Corre los tests de contrato.
  Si pasan: commit. Si no: explícame por qué y propon una corrección.

  Después seguimos con el siguiente endpoint.
💡 Un endpoint = un commit = un PR. Reviews y rollbacks fáciles.
4
Compactar antes de seguir 
> /compact mantén el plan de migración (5 fases),
  los endpoints ya migrados (health, status, version) y la suite
  de tests de contrato. Descarta los logs de errores resueltos
  y las exploraciones iniciales.
⚠ Errores comunes:
  • Migrar todo en un solo PR — review imposible y rollback nuclear
  • Sin tests de contrato — descubres regresiones en producción
  • Cambiar el contrato HTTP "de paso" — rompes clientes que no controlas
Flujo 05

👀 Code review profundo asistido

Situación: Te asignan revisar un PR de 800 líneas en 30 minutos. Tienes que dar feedback útil sin perderte detalles importantes.

1
Resumen ejecutivo del PR 
> Lee el diff actual con `git diff main...HEAD`.
  Dame un resumen ejecutivo en 5 puntos:
  - ¿Qué problema resuelve?
  - ¿Qué archivos toca y por qué?
  - ¿Hay cambios estructurales (nuevos módulos, refactors grandes)?
  - ¿Hay tests añadidos? ¿Qué cubren?
  - ¿Qué NO hace este PR (scope explícito)?
💡 El resumen te orienta antes de bucear en líneas concretas.
2
Revisión por checklist 
> Ejecuta /code-review (nuestro Skill).
  Quiero output organizado por prioridad:
  🔴 Bloqueantes — bugs, seguridad, romper compat
  🟡 Sugerencias — mejoras de diseño, naming
  🟢 Nits — typos, espaciado, comentarios

  Para cada hallazgo: archivo:línea + por qué + fix sugerido.
3
Verificación cruzada 
> Para cada hallazgo bloqueante, dame el código exacto que lo
  causaría a fallar. Si no puedes producir un caso concreto que falla,
  reclasifícalo a "sugerencia".
💡 Esto evita falsos positivos — bloquea solo lo que realmente bloquea.
⚠ Errores comunes:
  • Aceptar todo el feedback de Claude sin verificar — incluye falsos positivos
  • Bloquear nits — frustra al autor y desincentiva PRs pequeños
  • No pedir resumen ejecutivo — te pierdes en líneas sin contexto
Flujo 06

📚 Generar documentación OpenAPI desde el código

Situación: Tu API tiene 60 endpoints. Necesitas un OpenAPI 3.1 actualizado para que el equipo de mobile/frontend genere clientes tipados.

1
Inventario de endpoints 
> Encuentra todos los endpoints en @src/routes/ y @src/controllers/.
  Para cada uno extrae:
  - Método y ruta
  - Schema de request (path/query/body) — busca Zod schemas o tipos TS
  - Schema de response (success y errores)
  - Tag de dominio (auth, users, payments…)

  Devuélvelo como tabla Markdown.
2
Generar OpenAPI YAML 
> Con esa información, genera @docs/openapi.yaml en formato OpenAPI 3.1.
  Reglas:
  - Schemas reusables en components/schemas
  - Errores documentados (400, 401, 403, 404, 500)
  - Ejemplos por endpoint (mínimo 1)
  - Servers: dev/staging/prod con URLs reales de @CLAUDE.md
3
Validar el OpenAPI 
> Corre `npx @apidevtools/swagger-cli validate docs/openapi.yaml`.
  Si hay errores, corrígelos. Si todo está bien, instala
  @scalar/api-reference y genera una preview HTML del docs.
4
Hook para mantener actualizado 
> Crea un hook PostToolUse en @.claude/settings.json:
  cuando se modifique un archivo en src/routes/ o src/controllers/,
  ejecutar `npm run docs:generate` que regenera el OpenAPI parcialmente.
  Así nunca queda desactualizado.
💡 Hooks son tu mejor defensa contra docs obsoletas.
Flujo 07

⚡ Investigar un cuello de botella de performance

Situación: Tu endpoint GET /api/dashboard tarda 4.2s en p95. Los usuarios se quejan. Tienes que bajar a <500ms.

1
Trazar la llamada completa 
> Lee @src/api/dashboard.ts. Traza la ejecución completa:
  qué queries hace, en qué orden, qué se computa en memoria.
  Identifica candidatos a cuello de botella (N+1, queries sin índice,
  loops anidados, llamadas síncronas a servicios externos).

  Dame un ranking de hipótesis ordenado por probabilidad.
2
Medir antes de optimizar 
> Añade timings con console.time/timeEnd en cada sección sospechosa.
  Corre el endpoint con un payload realista (10 items en dashboard).
  Pega los timings de vuelta y dame el análisis.
💡 Optimizar sin medir = adivinar. Mide siempre primero.
3
Aplicar fix con benchmark 
> Aplica la optimización al cuello de botella #1 (la query N+1).
  Después corre los timings de nuevo y compara con el baseline.
  Si la mejora es <30%, descártala y prueba otra hipótesis.
4
Test de regresión de performance 
> Añade un test que falle si el endpoint tarda >800ms con el dataset
  de prueba estándar. Usa vitest con timeout custom. Esto previene
  regresiones de performance en futuros cambios.

Flujo 09

🧹 Refactor agresivo con red de seguridad

Situación: Una función God de 600 líneas controla todo el checkout. Quieres dividirla sin romper nada — y tienes 0 tests sobre ella.

1
Tests de caracterización primero 
> Lee @src/checkout/process.ts (la función God).
  Identifica TODOS los outputs observables: returns, side effects (DB writes,
  emails, eventos), errores que lanza.

  Genera tests de caracterización: capturan el comportamiento ACTUAL,
  no el ideal. Estos tests son tu red — si pasan después del refactor,
  no rompiste nada externo.

2
Identificar responsabilidades 
> En la función God, identifica las "fases" lógicas
  (validación, cálculo de precio, charge al pago, persistencia, notificación).

  Propon una división en módulos sin implementar nada todavía.
3
Refactor por fases con commits pequeños 
> Extrae SOLO la fase de validación a un módulo nuevo.
  La función original sigue funcionando, solo delega esa parte.
  Corre los tests de caracterización: deben seguir verdes.

  Commit. Después seguimos con la fase de cálculo de precio.

Nivel 2 Avanzado: MCP & Tokens

Conecta Claude Code a herramientas externas vía Model Context Protocol y aprende a gestionar tu ventana de contexto como un profesional.

2.1 — Model Context Protocol (MCP)

MCP es un estándar abierto creado por Anthropic que permite a Claude Code comunicarse con servicios externos (GitHub, Postgres, Slack, navegadores) vía servidores que exponen herramientas, recursos y prompts. Soporta tres transportes: stdio (local, baja latencia), SSE (remoto streaming) y HTTP. 

# Exporta tu token como variable de entorno (NO lo escribas en el JSON)
export GITHUB_TOKEN="ghp_tu_token_aqui"

# Registra el servidor MCP de GitHub (transporte stdio por defecto)
claude mcp add github -e GITHUB_TOKEN -- npx -y @modelcontextprotocol/server-github

# Verifica que esté conectado
claude mcp list
# Salida esperada:  github: connected (stdio)
# Servidor remoto SSE
claude mcp add --transport sse my-remote https://mi-servidor.com/mcp/sse

# Servidor remoto HTTP con headers de auth
claude mcp add --transport http composio-server "https://mcp.composio.dev/..." \
  --headers "X-API-Key:TU_API_KEY"

2.3 — Memoria persistente con /memory

2.4 — Configuración declarativa de MCP con .mcp.json

En lugar de ejecutar comandos claude mcp add manualmente, puedes declarar tus servidores MCP en un archivo .mcp.json en la raíz del proyecto. Claude Code lo cargará automáticamente al iniciar. 

{
  "mcpServers": [
    {
      "name": "github",
      "transport": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    },
    {
      "name": "postgres",
      "transport": "stdio",
      "command": "node",
      "args": ["./mcp-servers/postgres.js"],
      "env": {
        "DB_URL": "${DATABASE_URL}"
      }
    },
    {
      "name": "api-docs",
      "transport": "sse",
      "url": "https://mi-api.com/mcp/sse"
    }
  ]
}
💡 Tip: Versionea .mcp.json en git (sin secrets). Las variables ${...} se leen de variables de entorno en tiempo de ejecución.

3.0 — Comandos disponibles en Nivel 3

3.1 — Anatomía de una Skill

3.2 — Crear tu primera Skill: /security-audit

---
name: security-audit
description: Audita el código en busca de vulnerabilidades comunes
  (SQLi, XSS, secretos expuestos, configuraciones inseguras). Úsalo
  cuando el usuario mencione seguridad, hardening o revisión de
  vulnerabilidades.
allowed-tools: Read, Grep, Glob, Bash(git diff:*)
model: claude-opus-4-7
---

# Auditoría de Seguridad

Analiza el código del proyecto buscando:

1. **Inyección SQL** — queries construidas por concatenación
2. **XSS** — output sin escapar en plantillas / DOM
3. **Secretos expuestos** — keys, tokens, contraseñas en código
4. **Configuraciones inseguras** — CORS abierto, debug=true, etc.
5. **Dependencias vulnerables** — revisa package.json / requirements

Para cada hallazgo, devuelve:
- Archivo y línea exacta
- Severidad (crítica / alta / media / baja)
- Código actual + parche recomendado
- Referencia OWASP cuando aplique

Una vez guardado, la Skill está disponible inmediatamente. Invócala con /security-audit o deja que Claude la dispare automáticamente cuando detecte intención coincidente con el campo description.

3.3 — Skill con argumentos dinámicos

---
name: fix-issue
description: Resuelve un issue de GitHub siguiendo nuestras convenciones
argument-hint: [issue-number] [priority]
allowed-tools: Read, Edit, Bash(gh:*), Bash(git:*)
---

Resuelve el issue #$1 con prioridad $2.

Pasos:
1. `gh issue view $1` para leer la descripción
2. Crear branch `fix/issue-$1`

5. Crear commit + PR enlazado al issue

3.3+ — Orquestación de sub-agentes

Claude Code puede crear y orquestar sub-agentes — instancias paralelas de Claude que trabajan en paralelo en diferentes tareas. Perfecto para:

  • Investigación + Implementación: Un agente revisa requisitos mientras otro implementa.
  • Revisión paralela: Un agente audita seguridad, otro revisa tests, otro style.
  • Pipelines de datos: Agentes en serie: fetch → transform → validate → upload.
---
name: parallel-refactor
description: Refactoriza el código en paralelo
allowed-tools: Read, Edit, Bash(git:*), Task
---

# Refactorización en paralelo

Con la herramienta Task, crea dos sub-agentes:

```
!`claude task --name investigar -- grep -r "deprecated_func" src/`
!`claude task --name implementar -- "Reemplaza todas las llamadas encontradas"`
```

Espera a que ambas terminen (ambos agentes reportan estado).
Luego revisa cambios y haz commit.
🚀 Escalabilidad: Los sub-agentes heredan el contexto (CLAUDE.md, archivo.md, archivos mencionados) pero ejecutan independientemente. Úsalos para paralelizar trabajo costoso en tokens o tiempo.

  "permissions": {
    "allowedTools": ["Read", "Write", "Bash(git:*)", "Bash(npm:*)"],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Write(./production.config.*)"
    ]
  },
  "hooks": {
    "PostToolUse": [

🛡 4. Mitigar sesgos de seguridad en código generado

Los LLMs tienden a generar patrones inseguros si no se les corrige (ej. queries por concatenación, validación cliente-only, CORS abierto). Estrategias:

4.4 — Optimización de Tokens (40-60% ahorro)

En producción, los tokens son dinero. Estas 8 técnicas, combinadas, reducen costos entre 40% y 60%:

1. Prompt Caching

Marca el system prompt con cache_control: ephemeral. Tokens cacheados cuestan 10% del precio normal. TTL: 5 min.

{ "role": "system",
  "content": [{ "type": "text",
    "text": "Eres un asistente de código...",
    "cache_control": { "type": "ephemeral" }
  }]
}

2. Batch API

Para tareas latency-tolerant (análisis offline, migraciones). 50% descuento sobre precio normal. Hasta 100K requests por batch.

anthropic.beta.messages.batches.create({
  requests: files.map(f => ({
    custom_id: f.name,
    params: { model, messages: [...] }
  }))
})

3. Sumarización Jerárquica

Usa /compact antes de cambiar de tarea. Reduce contexto 70-80% manteniendo el hilo. El historial comprimido se cachea automáticamente.

4. Context Windowing

En pipelines largos, solo incluye el contexto relevante por tarea. Usa @archivo específico en vez de cargar el proyecto completo.

Regla 80/20: Prompt Caching solo ya ahorra ~40% en la mayoría de proyectos con system prompts repetidos. Empieza por ahí antes de optimizar otras dimensiones.

4.5 — Performance: 1000+ req/min

Para sistemas de producción con alta concurrencia, el cuello de botella suele ser la gestión de rate limits, no la latencia por request. 

{
  "model": "claude-opus-4-7",
  "effortLevel": "high",
  "permissions": { "defaultMode": "auto" },
  "rateLimiting": {
    "requestsPerMinute": 1000,
    "retryOnRateLimit": true,
    "maxRetries": 3,
    "backoffMs": 1000
  }
}

Arquitectura de 4 fases para escalar

Fase 1 (< 100 req/min):   Single model, sync calls
Fase 2 (100-500 req/min): Connection pooling + prompt cache
Fase 3 (500-1K req/min):  Batch API + async processing
Fase 4 (1K+ req/min):     Multi-region + queue system (SQS/BullMQ)

Errores de Contexto

Errores de Hooks

  • Hook no dispara: Verifica spelling del evento (camelCase exacto)
  • Permission denied: chmod +x hook.sh

Errores de Performance

  • Cache miss siempre: TTL es 5 min — system prompt debe ser idéntico

  • Batch nunca completa: Verifica webhook o usa polling con batches.retrieve()

      type: 'object',
      properties: {
        command: { type: 'string', description: 'Comando a ejecutar' }
      },
      required: ['command']
    }
  }
];

async function runAgent(userMessage: string) {
  const messages: Anthropic.MessageParam[] = [
    { role: 'user', content: userMessage }
  ];

  while (true) {
    const response = await client.messages.create({
      model: 'claude-sonnet-4-6',
      max_tokens: 4096,
      tools,
      messages
    });

    // Añadir respuesta al historial
    messages.push({ role: 'assistant', content: response.content });

    if (response.stop_reason === 'end_turn') break;

    if (response.stop_reason === 'tool_use') {
      const toolResults: Anthropic.ToolResultBlockParam[] = [];

      for (const block of response.content) {
        if (block.type !== 'tool_use') continue;

        let result = '';
        if (block.name === 'read_file') {
          result = readFileSync((block.input as any).path, 'utf8');
        } else if (block.name === 'run_bash') {
          result = execSync((block.input as any).command, { encoding: 'utf8' });
        }

        toolResults.push({
          type: 'tool_result',
          tool_use_id: block.id,
          content: result
        });
      }

      messages.push({ role: 'user', content: toolResults });
    }
  }

  // Extraer texto final
  const lastMsg = messages[messages.length - 1];
  const content = Array.isArray(lastMsg.content) ? lastMsg.content : [];
  return content.find(b => b.type === 'text')?.text ?? '';
}

// Uso

  'Lee @src/index.ts y dame un resumen de la arquitectura'
);

async function chat(userMessage: string) {
  const messages: Anthropic.MessageParam[] = [
    { role: 'user', content: userMessage }
  ];

  let response = await client.messages.create({
    model: 'claude-sonnet-4-6',
    max_tokens: 1024,
    tools,
    messages
  });

  // Bucle de tool use
  while (response.stop_reason === 'tool_use') {
    messages.push({ role: 'assistant', content: response.content });

    const results: Anthropic.ToolResultBlockParam[] = response.content
      .filter(b => b.type === 'tool_use')
      .map(block => {
        const b = block as Anthropic.ToolUseBlock;
        const input = b.input as Record;

        const result = b.name === 'get_weather'
          ? get_weather(input.city, input.unit)
          : search_database(input.query, input.limit);

        return {
          type: 'tool_result' as const,
          tool_use_id: b.id,
          content: JSON.stringify(result)
        };
      });

    messages.push({ role: 'user', content: results });

    response = await client.messages.create({
      model: 'claude-sonnet-4-6',
      max_tokens: 1024,
      tools,
      messages
    });
  }

  const textBlock = response.content.find(b => b.type === 'text');
  return textBlock?.type === 'text' ? textBlock.text : '';

async function safeRequest(prompt: string) {
  try {
    const response = await client.messages.create({
      model: 'claude-sonnet-4-6',
      max_tokens: 1024,
      messages: [{ role: 'user', content: prompt }]
    });
    return { ok: true, data: response };

  } catch (err) {
    if (err instanceof Anthropic.APIError) {
      switch (err.status) {
        case 400: return { ok: false, error: `Bad Request: ${err.message}` };
        case 401: return { ok: false, error: 'API Key inválida o expirada' };
        case 403: return { ok: false, error: 'Sin permisos para este recurso' };
        case 429: return { ok: false, error: 'Rate limit — reduce la frecuencia' };
        case 529: return { ok: false, error: 'API sobrecargada — reintenta más tarde' };
        default:  return { ok: false, error: `Error ${err.status}: ${err.message}` };
      }
    }
    throw err;   // Re-lanzar errores inesperados
  }
}

          node-version: '22'

        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}

          DIFF=$(git diff origin/${{ github.base_ref }}...HEAD)

        uses: actions/github-script@v7
        with:
          script: |

            const body = `## 🤖 Claude Code Review\n\n` +
              `**Resumen:** ${review.summary}\n\n` +
              (review.blockers.length ? `### 🔴 Bloqueantes\n${review.blockers.map(b => `- ${b}`).join('\n')}\n\n` : '') +
              (review.suggestions.length ? `### 💡 Sugerencias\n${review.suggestions.map(s => `- ${s}`).join('\n')}` : '');

            await github.rest.issues.createComment({
              owner: context.repo.owner,
              repo: context.repo.repo,

name: Security Scan
on:
  push:
    branches: [main, develop]
  pull_request:

jobs:
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - run: npm install -g @anthropic-ai/claude-code

      - name: Security Audit
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          # Archivos modificados en el PR/push
          FILES=$(git diff --name-only HEAD~1 -- '*.ts' '*.js' '*.py' 2>/dev/null || \
                  git diff --name-only origin/main...HEAD -- '*.ts' '*.js' '*.py')

          if [ -z "$FILES" ]; then
            echo "No hay archivos de código modificados"
            exit 0
          fi

          FOUND_ISSUES=false

          for FILE in $FILES; do
            if [ ! -f "$FILE" ]; then continue; fi

            RESULT=$(claude -p \
              "Analiza SOLO este archivo buscando:
               1. SQL injection (queries por concatenación)
               2. XSS (output sin escapar)
               3. Secretos hardcodeados (keys, passwords, tokens)
               4. CORS inseguro
               5. Ejecución de comandos sin sanitizar
               Si encuentras algo crítico devuelve JSON: {\"critical\": true, \"issues\": [...]}
               Si está limpio devuelve: {\"critical\": false}" \
              < "$FILE" --output-format json --dangerously-skip-permissions)

            CRITICAL=$(echo $RESULT | jq -r '.critical // false')
            if [ "$CRITICAL" = "true" ]; then
              echo "❌ CRÍTICO en $FILE:"
              echo $RESULT | jq -r '.issues[]'
              FOUND_ISSUES=true
            else
              echo "✅ Limpio: $FILE"
            fi
          done

          if [ "$FOUND_ISSUES" = "true" ]; then
            exit 1
          fi

CI-5 — Script de migración asistida

#!/bin/bash
# Migración asistida de JS → TS con Claude Code
# Uso: ./scripts/migrate-with-claude.sh src/utils/

set -e
TARGET_DIR=${1:-src/}
CLAUDE_OPTS="--dangerously-skip-permissions"

echo "🔄 Iniciando migración JS→TS en $TARGET_DIR"

# Encontrar todos los .js (excluyendo node_modules y config)
JS_FILES=$(find "$TARGET_DIR" -name "*.js" \
  -not -path "*/node_modules/*" \
  -not -name "*.config.js" \
  -not -name "*.test.js")

TOTAL=$(echo "$JS_FILES" | wc -l)
COUNT=0

for FILE in $JS_FILES; do
  COUNT=$((COUNT + 1))
  echo "[$COUNT/$TOTAL] Migrando $FILE..."

  TS_FILE="${FILE%.js}.ts"

  # Claude migra el archivo con tipos estrictos
  claude -p \
    "Migra este archivo JavaScript a TypeScript estricto.
     - Infiere tipos desde el uso (no uses 'any')
     - Añade interfaces para objetos complejos
     - Preserva toda la lógica de negocio sin cambios
     - Actualiza imports para usar extensión .ts
     - NO cambies el comportamiento observable
     Devuelve SOLO el código TypeScript, sin explicaciones ni backticks." \
    < "$FILE" $CLAUDE_OPTS > "$TS_FILE"

  # Verificar que compila
  if npx tsc --noEmit "$TS_FILE" 2>/dev/null; then
    echo "  ✅ $TS_FILE compila correctamente"
    rm "$FILE"  # Eliminar original JS
  else
    echo "  ⚠️  $TS_FILE tiene errores de tipo — revisar manualmente"
    rm "$TS_FILE"  # Mantener original JS si hay errores
  fi

  # Rate limiting: no sobresaturar la API
  sleep 0.5
done

echo "✅ Migración completada: $COUNT archivos procesados"
echo "💡 Ejecuta 'npm run typecheck' para verificar el proyecto completo"

¿Qué es Claude Code?

Claude Code es una forma completamente diferente de trabajar. En lugar de escribir todo manualmente, le cuentas qué quieres y Claude lo entiende de inmediato, considerando todo tu proyecto.

3 Razones clave:

  • 💨 Más rápido: No escribes código repetitivo, Claude lo genera por ti.
  • 🎯 Entiende tu contexto: Conoce tu proyecto completo, no solo una función.
  • 🔄 Aprende tu estilo: Recuerda tus decisiones y preferencias entre sesiones.

Glosario: Términos que necesitas conocer

Explicaciones simples de términos técnicos, con analogías y ejemplos reales.

Contexto

Definición simple: Información que Claude Code recuerda durante tu sesión.

Analogía: Es como tu conversación con un amigo — mientras más le dices, mejor te entiende.

Ejemplo: Si subes un archivo de datos, Claude lo recuerda para los siguientes comandos. Si mencionas que eres un PM, recordará eso.

Token

Definición simple: Una pequeña unidad de texto, aproximadamente una palabra.

Analogía: Son como monedas del lenguaje. Cada pregunta y respuesta gasta cierta cantidad de tokens.

Ejemplo: Una pregunta simple = ~50 tokens. Un documento de 5 páginas = ~2000 tokens.

MCP (Model Context Protocol)

Definición simple: Conexiones a herramientas especiales que Claude Code puede usar.

Analogía: Como enchufes especializados. Puedes conectar GitHub, Slack, Jira, etc., y Claude accede a ellos automáticamente.

Ejemplo: Con MCP de GitHub, Claude puede leer tus commits sin que le copies manualmente el código.

Skill

Definición simple: Un comando personalizado que creas para tareas repetitivas.

Analogía: Como una receta: defines los pasos una vez y luego la reutilizas infinitas veces.

Ejemplo: Crear `/analizar-feedback` — tu Skill personalizado que procesa customer feedback automáticamente.

Memoria

Definición simple: Información que Claude Code guarda entre sesiones.

Analogía: Tu cuaderno personal: no olvida decisiones, preferencias y contexto del proyecto.

Ejemplo: Guardar "usa siempre TypeScript en este proyecto" y Claude lo recordará mañana, la próxima semana, siempre.

Comando

Definición simple: Una instrucción que empiezas con `/` o que ejecutas en la terminal.

Analogía: Como accesos rápidos o atajos: `/help` = pedir ayuda, `/clear` = empezar de cero.

Ejemplo: Escribes `/model claude-opus-4-7` para cambiar al modelo más potente.

🌿 Branching Strategy — Ramas con Claude Code

Estructura de ramas + Claude worktrees para desarrollo sin conflictos. Integración con CI/CD automatizado.

⚡ Quick Start

git checkout -b feature/x
claude --worktree feature-x
/memory add "Feature X: description"
/checkpoint "Milestone 1 done"
# → Continúa sin conflictos de contexto

📊 Comparativa de Estrategias

🎯 Trunk-Based Development

Cuándo usar: Equipos 2-8, releases diarias/semanales, CI/CD sólido

git checkout -b fix/issue-247
# Max 1 día de desarrollo
git commit -m "fix: ..."
git push && # PR → Code review → Merge immediatamente
git checkout master && git pull
# ✅ Deploy automático vía CI/CD
✓ Menos conflictos
✓ Deploy seguro
✓ Feedback rápido
✗ Requiere CI/CD confiable
✗ Tests deben pasar siempre
✗ Presión para merge rápido

📊 Gitflow (Feature Branches)

Cuándo usar: Equipos 8-20, releases planeadas (mensuales), varias versiones en producción

master (producción) ← releases←release/v2.0
develop (próximo release)←feature/auth

git checkout -b feature/oauth develop
# 3-7 días de desarrollo
git commit, git push
# PR: feature → develop → Merge cuando feature completa
# Release: develop → release/v2.0 → master (tagged)
✓ Trabajo en paralelo
✓ Release planning claro
✓ Hotfix ramificado
✗ Puede ser complejo
✗ Merges frecuentes
✗ Mayor admin de ramas

🔀 Git Worktrees + Claude Code

Cuándo usar: Multitarea simultánea, refactors largos, sin conflictos de contexto

# Terminal 1: Worktree para feature/auth
git worktree add refactor-auth feature/auth
cd refactor-auth && claude --worktree auth
/memory add "Auth refactor: phase 1"

# Terminal 2: Worktree para feature/payment (sin conflictos)
git worktree add feature-payment feature/payment
cd feature-payment && claude --worktree payment
# Contexto completamente aislado
✓ Contexto aislado
✓ Multitarea sin conflictos
✓ Tests en paralelo
✗ Requiere entender worktrees
✗ Cleanup manual
✗ Disco: +copia de archivos

🔧 Patrones principales con Claude Code:

Feature Branches + Worktrees

Cada feature en rama + worktree aislado. Claude mantiene contexto separado, sin conflictos de historial.

claude --worktree feature-auth
/memory add "Auth: OAuth2 implementation"
/checkpoint "OAuth config done"
# → Próxima sesión retoma con: /rewind

Long-Lived Branches + Memory Sync

Para refactors largos (5+ días): guarda automáticamente progreso con Memory.

git checkout -b refactor/database-v2
/memory add "Phase 1: Migrate users table"
/checkpoint "Migration tested, ready for phase 2"
# Día 2: retomar con /rewind + /memory search

Hotfix + Production Safety

Para emergencias: worktree + permission-mode. Merge rápido a main + develop con auto-tags.

git checkout -b hotfix/csrf-vulnerability
claude --permission-mode allow-push
# Fix rápido + commit
git push && git tag hotfix/v1.2.1
# → CI/CD deploy automático a producción

Release Management

Rama dedicada para release: estabilización, bump version, changelog, deploy coordinado.

# Cuando develop está estable
git checkout -b release/v2.0 develop
# Claude solo hace: bump version, changelog, tests
git commit -m "release: v2.0 - changelog"
git push && # PR → Merge → Tag v2.0
# Back-merge a master + develop

🔗 Integración con CI/CD

GitHub Actions / GitLab CI: Valida automáticamente antes de merge

on: [pull_request]
jobs:
  lint: run: npm run lint
  test: run: npm test
  build: run: npm run build
  security: run: npm audit

# Si pasa → Auto-merge (Trunk-Based)
# Si falla → Bloquea merge, comenta en PR

Deploy automático: Después de merge a master

on: push to master
jobs:
  deploy: run: vercel deploy --prod
  smoke-tests: run: npm run test:e2e
  notify: post to Slack: "v1.2.3 deployed"

📈 Diagrama de flujo

Trunk-Based (simple):
master ←← feature/x ← (1 día) ← PR ← Merge ← Deploy ✅

Gitflow (complicado):
master ← release/v2.0 ← develop ← feature/auth
        ↓
     (tagged)        ← Hotfix branch
        ↓
      v2.0 → Deploy a producción

Worktrees (paralelo):
    Worktree A: feature/auth
    Worktree B: feature/payment   ← Sin conflictos
    Worktree C: hotfix/critical  ← Contexto aislado
                                  ← Merge independiente

📋 .rules & Config — Reglas Determinísticas & Validación Pre-Deploy

Rules = instrucciones que se aplican automáticamente en cada sesión. Configuración versionada en git + validación en git hooks y CI/CD.

¿Qué son las Rules y por qué importan?

Rules = instrucciones que SIEMPRE se ejecutan automáticamente en cada sesión de Claude Code.

Skills = sugerencias que Claude considera aplicar opcionalmente.

Diferencia clave: Las rules son determinísticas y versionadas en git — todo dev sigue exactamente las mismas.

Para qué sirven: Garantizar consistencia de código, evitar bugs comunes, asegurar seguridad, mantener testing, validar pre-deploy. Son especialmente útiles en equipos donde múltiples devs trabajan en paralelo.

🔗 Rules & Git Hooks: Integración Completa

¿Cómo funciona? Rules en .claude/CLAUDE.md se ejecutan automáticamente. Para validarlas localmente antes de push, usas git hooks (husky):

.claude/CLAUDE.md (rules: code style, testing, security)
↓
Cada sesión de Claude Code aplica estas rules automáticamente
↓
.husky/pre-commit (ejecuta: lint, type-check, tests)
↓
Git bloquea commit si viola alguna rule
↓
GitHub Actions / CI ejecuta validación adicional
↓
PR bloqueado si hay violations, hasta que se arreglen

.claude/

.husky/

└── pre-push # Valida antes de push (security scan, audit)

🔐 Ejemplo 1: Rules para Security (Bloquear Credentials)

Evita que se cometan archivos .env, API keys, o cualquier credencial sensible.

# .claude/rules.local.md (GITIGNORE)

## Environment Variables
- Nunca hardcodear secrets en código
- .env: GITIGNORE + .env.example públicamente
- API Keys: solo en environment variables
- Database URLs: nunca en código fuente
- Tokens OAuth: almacenar encriptados en DB

## Pre-commit Validation
- Husky bloquea commits con strings "PASSWORD", "API_KEY", "SECRET"
- Scan de archivos sensibles: .pem, .key, .crt
- Busca credenciales en strings entre comillas
- Ejemplo: Si haces `password = "abc123"` → COMMIT BLOQUEADO

## Comando: Generar .env.example
```
npm run generate:env-example
# Genera .env.example sin valores, solo keys
```

Validaciones que deben pasar ANTES de hacer deploy.

# .claude/rules.md - Production Section

## Pre-Deploy Checklist
- TypeScript: npm run type-check (ZERO errors)
- Tests: npm test -- --coverage 80%
- Security: npm audit --audit-level=moderate (ZERO high/critical)
- Linting: npm run lint (ZERO violations)
- Build: npm run build (succeeds, no warnings)

- Database: migraciones versionadas en git (solo via migrations/)

- Antes de deploy: backup de DB
- Deployment: canary → 10% → 50% → 100%
- Monitoring: 10min después de 100% rollout
- Si error: git revert + npm run deploy

📅 Cuándo Actualizar y Revisar Rules

📊 Sprint Review (Cada 2 semanas)

En retrospectiva: ¿qué rules funcionaron? ¿Cuáles fueron obstáculos?

  • ¿Alguien violó una rule más de 3 veces?
  • ¿Hay confusión sobre cómo aplicar la rule?
  • ¿La rule ayudó a evitar bugs?

🆕 Cuando agregas nueva dependencia

Cada librería nueva puede necesitar una rule nueva.

  • npm install react → agregar rule sobre hooks
  • npm install eslint → actualizar .eslintrc.json
  • npm install prisma → agregar rule sobre migrations

🐛 Después de cada bug importante

Bug crítico = falta una rule. Agregala inmediatamente.

  • SQL injection attack → agregar rule: validación obligatoria
  • Performance issue → agregar rule: indexing requirement
  • Deploy fallido → agregar rule: pre-deploy validation

✨ Cuando team crece

Más devs = más necesidad de rules claras.

  • 1-2 devs: rules básicas (style, security, tests)
  • 5+ devs: rules detalladas (naming, architecture, deployment)
  • 10+ devs: rules por especialidad (frontend rules ≠ backend)

🚨 Troubleshooting: Rules que no Funcionan

❌ Problema: Devs ignoran las rules

Las rules están en CLAUDE.md pero nadie las lee

Solución:

  • Hacer pre-commit hooks: fuerza a que se ejecuten
  • Documentar WHY: no solo WHAT, explica el por qué
  • Excepciones documentadas: si hay, usar // rule:skip con motivo

❌ Problema: Pre-commit hook no se ejecuta

npm run lint nunca se ejecuta antes de commit

Solución:

npm install husky --save-dev
npx husky install
npx husky add .husky/pre-commit "npm run lint && npm test"
git add .husky/pre-commit
git commit -m "chore: add git hooks"

❌ Problema: Regla demasiado estricta, bloquea todo

coverage: 95% = nadie puede hacer commit

Solución:

  • Bajar a 80% (pragmático, todavía riguroso)
  • Permitir excepciones con eslint-disable + motivo
  • Revisar: quizás falta entrenamiento, no que rule sea mala

❌ Problema: Conflicto entre rules (rule A contradice rule B)

"Usa try/catch" vs "nunca captures excepciones"

Solución:

  • Reunión urgente: aclarar cuál regla prevalece
  • Documentar contexto: cuándo se aplica cada rule
  • Test: escribir ejemplo de código que satisface ambas

💾 Memory Management — Token Limits & Persistencia Entre Sesiones

Sistema de memoria en 3 niveles. Explora contexto, límites de tokens, estrategias de compactación, forks, y persistencia sin contaminar contexto.

¿Por qué Memory Importa? (Contexto & Token Limits)

Contexto (Context Window) = cantidad de tokens que un modelo puede procesar. Claude Haiku: 200k tokens. Claude Opus: 200k tokens.

Token Limit Problem: Después de 3-5 días de trabajo intenso, la conversación puede alcanzar 100k+ tokens, dejándote sin espacio para nuevo código.

Día 1: 10k tokens (inicio, leer proyecto)
Día 2: 40k tokens (primeras features)
Día 3: 80k tokens (refactor + bugs)
Día 4: 150k tokens ← CASI LLENO, poco espacio para nuevo trabajo
Día 5: 190k tokens ← BLOQUEADO, no puedes continuar

Solución: /memory compact en Día 3 → 150k → 50k (3x más espacio)

Diferencia clave: Memory ≠ Conversation History. Memory es persistente, comprimible, versionada. Conversation crece sin límite.

🔵 3 Niveles de Memory: Session, Project, Global

🔵 Session Memory

Alcance: Esta sesión solo (se pierde al cerrar)

Volatile, rápido acceso, temporal

Ejemplos: "Context from last message", variables locales

📁 Project Memory

Alcance: Todos los devs del proyecto

Versionado en git: .claude/memory/

Ejemplos: arquitectura, decisiones, APIs

🌍 Global Memory

Alcance: Todos tus proyectos (permanente)

Local: ~/.claude/memory/

Ejemplos: patrones, soluciones, best practices

📊 Entender Contexto y Token Limits

¿Qué es un Token? Aproximadamente 1 token = 4 caracteres. Un párrafo de 200 caracteres = 50 tokens.

Token Budget (Claude Haiku):
Total context: 200,000 tokens
Reserved para output: 4,000 tokens
Available para input: 196,000 tokens

Si conversation = 150k tokens:
→ Espacio restante: 46k (suficiente para 200KB de código nuevo)
Señales de Alerta:
  • Claude dice: "approaching token limit"
  • Respuestas empiezan a ser más cortas
  • Errores: "context length exceeded"
  • Sesión que lleva 3-4 días intensos

🗜️ Estrategia 1: Compactación (/memory compact)

Cuándo usar: Cuando memoria > 10KB o después de 2-3 días de trabajo intenso.

¿Qué hace? Remueve ruido (logs, dead ends, failed experiments) manteniendo conocimiento útil.

# Estado actual: 20KB memory
# Contiene: API decisions, DB schema, refactor logs, failed hypothesis

/memory compact "Keep: API v1→v2 decisions, DB schema optimizations.
                        Drop: Failed hypothesis #1, #2, debug logs, dead code experiments"

# Resultado: 20KB → 5KB
# Impacto en tokens: Conversation 150k → 135k (-15k), +15k espacio nuevo

Costo/Beneficio: -5% context size, +50% nuevos tokens disponibles. Muy recomendado cada 3 días.

🔀 Estrategia 2: Memory Forks (/memory fork)

Cuándo usar: Ramas de larga duración (feature branches, refactors). Experimentos sin afectar main.

¿Qué hace? Crea snapshot aislado de memoria para rama específica.

# main branch: memoria con [architecture, API spec, DB schema]

git checkout -b feature/experimental-db
/memory fork "experimental-db"

❌ Solución Mala #2: Ignorar y continuar

Sesión falla de repente, pierdes trabajo no guardado.

Preserva contexto, limpia memory, continúa trabajando.

📝 CLAUDE.md: Tu System Prompt Persistente

Estructura, convenciones y reglas de tu proyecto en un archivo que Claude Code lee automáticamente en cada sesión.

¿Qué es CLAUDE.md?

CLAUDE.md es un archivo especial (markdown) que Claude Code lee automáticamente al iniciar una sesión en tu proyecto. Actúa como una "memoria persistente" que define cómo debe comportarse Claude en tu contexto específico.

Define automáticamente:

  • Stack técnico: Versiones de frameworks, lenguajes, herramientas (Next.js 16, React 19, Node 20, etc.)
  • Convenciones de código: Naming (camelCase, PascalCase), patrones de estructura, imports
  • Comandos útiles: Scripts para dev, test, build, deploy que Claude puede sugerir/usar
  • Reglas de código: Lo que Claude DEBE hacer (inmutabilidad, tests) y lo que NO DEBE (modificar schema sin migration)
  • Arquitectura y gotchas: Decisiones de diseño, limitaciones, patterns especiales del proyecto
  • Integraciones MCP: Conexiones a GitHub, bases de datos, APIs internas
💡 Tip: CLAUDE.md se actualiza cada vez que cambias el proyecto. Mantenlo sincronizado para máxima efectividad.

Troubleshooting: Errores comunes

❌ "command not found: claude"

Causa: npm global bin no está en PATH.

# Encuentra dónde npm instala globales
npm config get prefix
# Debería devolver /usr/local o similar

# Agrega a tu .bashrc o .zshrc
export PATH="/usr/local/bin:$PATH"

# Recarga shell
source ~/.bashrc

❌ "npm ERR! code EACCES (Permission denied)"

Causa: npm requiere permisos de admin.

# Opción A: Usa sudo (simple pero no recomendado)
sudo npm install -g @anthropic-ai/claude-code

# Opción B: Cambia permisos npm (recomendado)
mkdir ~/.npm-global
npm config set prefix '~/.npm-global'
export PATH="~/.npm-global/bin:$PATH"
npm install -g @anthropic-ai/claude-code

Solución: Re-autentica.

# Elimina token anterior
rm ~/.anthropic/token.json

# Inicia sesión nuevamente
claude auth login

Causa: Instalación incompleta o antivirus bloqueó descarga.

# Limpia instalación
npm uninstall -g @anthropic-ai/claude-code
npm cache clean --force
npm install -g @anthropic-ai/claude-code

Producción / Git Workflows Detallado

🌿 Git Workflows Reales en Producción

Tres flujos probados: Trunk-based, Gitflow, Worktrees. Con comandos copy-paste.

Flujo A: Trunk-Based Development

Para: Equipos 2-8 personas, ciclos cortos (diarios/semanales)

# 1. Sincroniza master
git checkout master && git pull origin master

# 2. Feature branch corta (max 1 día)
git checkout -b fix/auth-token-refresh

# 3. Commits atómicos
git commit -m "fix: refresh token antes de expiración
- Valida expiration en middleware
- Usa /refresh endpoint
- Tests en auth.spec.ts"

# 4. Push + PR
git push -u origin fix/auth-token-refresh

# 5. Cleanup
git checkout master
git pull origin master
git branch -d fix/auth-token-refresh

Pros: Integración continua = menos conflictos, deploy seguro, feedback rápido

Contras: Requiere CI/CD sólido, tests confiables, presión para merge rápido

Flujo B: Feature Branches + Gitflow

Para: Equipos 8-20 personas, releases planeadas cada 2-4 semanas

# STEP 1: Feature branch desde develop
git checkout -b feature/otp-auth develop
git commit -m "feat: agregar TOTP authentication"
git push origin feature/otp-auth

# STEP 2: Code freeze para release
git checkout -b release/2.5.0 develop
git commit -m "chore: bump to v2.5.0"

# STEP 3: Tests finales + tag
npm test && npm run build
git tag -a v2.5.0 -m "Release 2.5.0"

# STEP 4: Merge a master + back a develop
git checkout master && git pull origin master
git merge --no-ff release/2.5.0
git push origin master v2.5.0

Pros: Estructura clara (develop ≠ production), releases controladas, hotfixes sin afectar features

Contras: Más complicado, merge frequentes, riesgo de divergencia

Flujo C: Git Worktrees (Paralelismo)

Para: Trabajar en 2-3 branches en paralelo sin conflictos

# Opción 1: Manual git worktree
git worktree add ~/work/auth-refactor -b feature/auth-refactor
cd ~/work/auth-refactor

# Opción 2: Automático con Claude Code
claude --worktree feature/auth-refactor

# Listing
git worktree list

# Cleanup
git worktree remove ~/work/auth-refactor

Pros: Paralelismo sin conflictos, contexto aislado, sin "git checkout"

Contras: Requiere más storage, puede ser confuso con directorios, cleanup manual

Producción / Hooks en Producción

🎣 Hooks para Seguridad & Automación

5 hooks reales que automatizan seguridad, tests y monitoreo.

Hook 1: Security Audit (PreToolUse)

Valida cada acción antes de ejecutarla — bloquea comandos peligrosos.

{
  "hooks": {
    "PreToolUse": {
      "enabled": true,
      "rules": [
        {
          "name": "Block dangerous commands",
          "pattern": "(rm -rf|eval|curl.*\\||sh -c|sudo)",
          "action": "block",
          "message": "Comando potencialmente peligroso."
        },
        {
          "name": "Block PII exposure",
          "pattern": "(password|token|secret)\\s*=",
          "action": "block",
          "message": "No se permite escribir credenciales."
        }
      ]
    }
  }
}

Hook 2: Auto-Format + Tests (PostToolUse)

Después de escribir código, formatea automáticamente y corre tests.

{
  "hooks": {
    "PostToolUse": {
      "enabled": true,
      "sequence": [
        { "name": "Format code", "command": "npm run format", "onError": "warn" },
        { "name": "Lint check", "command": "npm run lint", "onError": "warn" },
        { "name": "Run tests", "command": "npm test -- --watch=false", "onError": "abort" }
      ]
    }
  }
}

Hook 3: Context Injection (UserPromptSubmit)

Inyecta automáticamente contexto relevante antes de procesar prompts.

{
  "hooks": {
    "UserPromptSubmit": {
      "enabled": true,
      "injections": [
        { "name": "Git status", "command": "git status -s", "inject": true },
        { "name": "Session memory", "command": "head -20 ~/.claude/memory", "inject": true }
      ]
    }
  }
}

Hook 4: Cost Warning (PreToolUse)

Advierte si una acción va a consumir muchos tokens o hacer muchas API calls.

{
  "hooks": {
    "PreToolUse": {
      "enabled": true,
      "costWarnings": [
        { "name": "Large file", "pattern": "@.*(\\.log|\\.csv)", "fileSize": "10MB", "action": "warn" },
        { "name": "Database bulk op", "pattern": "DELETE|DROP|TRUNCATE", "action": "warn" }
      ]
    }
  }
}

Hook 5: Performance Monitoring (PostToolUse)

Registra timing, tokens y recursos de cada acción para análisis posterior.

{
  "hooks": {
    "PostToolUse": {
      "enabled": true,
      "monitoring": {
        "logFile": "~/.claude/performance.log",
        "metrics": ["duration", "tokensUsed", "errorsEncountered"],
        "alerts": [{ "metric": "duration", "threshold": "60s", "action": "log" }]
      }
    }
  }
}

Cómo Aplicar Hooks

# Crea archivo .claude.json en raíz de tu proyecto
cat > .claude.json << 'EOF'
{
  "hooks": {
    "PreToolUse": { ... },
    "PostToolUse": { ... }
  }
}
EOF

# Claude Code los carga automáticamente en cada sesión
cd tu-proyecto && claude
# Los hooks están activos

Claude Code vs Frameworks: Matriz de Decisión

Claude Code CLI (Puro)

  • Flujo interactivo developer-machine
  • Control manual paso a paso
  • Mejor para debugging y exploración
  • Menos overhead, más rápido
  • Ideal: refactor, review, setup

LangChain (Recomendado)

  • Orquestación predefinida de agentes
  • Integración con 200+ herramientas
  • Chain/RAG/Memory built-in
  • Ideal: pipelines de datos, RAG
  • Complejidad media, documentación excelente

CrewAI (Flexible)

  • Rol-basado multi-agente
  • Task-driven workflows
  • Más flexible que LangChain
  • Ideal: equipos virtuales, equipos multidisciplinarios
  • Comunidad creciente, ideal experimental

import Anthropic from "@anthropic-ai/sdk";
import { Tool } from "@langchain/core/tools";
import { AgentExecutor, createToolCallingAgent } from "langchain/agents";
import { ChatPromptTemplate } from "@langchain/core/prompts";
import { ChatAnthropic } from "@langchain/anthropic";

// 1. Definir tools
const tools: Tool[] = [
  {
    name: "grep_codebase",
    description: "Busca patterns en el código fuente",
    schema: {
      type: "object",
      properties: {
        pattern: { type: "string" },
        path: { type: "string" }
      },
      required: ["pattern"]
    }
  },
  {
    name: "read_file",
    description: "Lee contenido de archivo",
    schema: {
      type: "object",
      properties: {
        path: { type: "string" }
      },
      required: ["path"]
    }
  }
];

// 2. Crear agente Claude
const model = new ChatAnthropic({
  modelName: "claude-3-5-sonnet-20241022",
  temperature: 0,
  apiKey: process.env.ANTHROPIC_API_KEY
});

const prompt = ChatPromptTemplate.fromMessages([
  ["system", "Eres un agente experto en código. Usa las tools disponibles."],
  ["human", "{input}"],
  ["ai", "{agent_scratchpad}"]
]);

const agent = createToolCallingAgent({ llm: model, tools, prompt });
const agentExecutor = new AgentExecutor({ agent, tools, verbose: true });

// 3. Ejecutar
const result = await agentExecutor.invoke({
  input: "¿Cuáles son las funciones export en src/utils?"
});
console.log(result.output);

from crewai import Agent, Task, Crew, Process
from crewai_tools import FileReadTool, DirectoryReadTool
from anthropic import Anthropic

# 1. Definir agentes (roles)
code_reviewer = Agent(
    role="Code Reviewer",
    goal="Revisar cambios de código para calidad y seguridad",
    backstory="Expert revisor con 15 años de experiencia.",
    tools=[FileReadTool(), DirectoryReadTool()],
    verbose=True
)

security_specialist = Agent(
    role="Security Specialist",
    goal="Identificar vulnerabilidades de seguridad",
    backstory="Security expert certificado.",
    tools=[FileReadTool()],
    verbose=True
)

performance_analyst = Agent(
    role="Performance Analyst",
    goal="Detectar cuellos de botella y optimizaciones",
    backstory="Performance tuning specialist.",
    tools=[FileReadTool()],
    verbose=True
)

# 2. Definir tareas
review_task = Task(
    description="Revisar @{file_path}: estructura, claridad, testing",
    agent=code_reviewer,
    expected_output="Reporte detallado con issues y sugerencias"
)

security_task = Task(
    description="Analizar @{file_path} para vulnerabilidades comunes",
    agent=security_specialist,
    expected_output="Lista de riesgos de seguridad con severidad"
)

perf_task = Task(
    description="Analizar performance y proponer optimizaciones",
    agent=performance_analyst,
    expected_output="Análisis de complejidad + sugerencias"
)

# 3. Crear equipo
crew = Crew(
    agents=[code_reviewer, security_specialist, performance_analyst],
    tasks=[review_task, security_task, perf_task],
    process=Process.sequential,  # O Process.hierarchical
    verbose=True
)

# 4. Ejecutar
result = crew.kickoff(inputs={"file_path": "src/api/handlers.ts"})
print(result)
