Niveles / Nivel 1

Nivel 1 Fundamentos

Tu primera sesión productiva con Claude Code: instalar, autenticar y conocer los comandos esenciales que usarás a diario.

1.1 — Instalación

Claude Code requiere Node.js 18+ (recomendado 22 LTS). Hay dos vías oficiales:

# Instalación global con npm
npm install -g @anthropic-ai/claude-code

# Verificar la instalación
claude --version

# Iniciar la primera sesión en tu proyecto
cd mi-proyecto/
claude
# macOS, Linux, WSL
curl -fsSL https://claude.ai/install.sh | bash

# Windows PowerShell
irm https://claude.ai/install.ps1 | iex

1.2 — Autenticación

Antes de tu primera sesión, debes autenticar con Anthropic. Claude Code soporta dos modos: OAuth (recomendado) o API Key manual. 

# Abre tu navegador automáticamente para login
claude auth login

# Tras autenticar, verifica que estés logueado
claude --version
# Salida: claude-code 2.1.x | Authenticated as: tu@email.com
# Obtén tu API Key en https://console.anthropic.com
# Luego exporta la variable de entorno
export ANTHROPIC_API_KEY="sk-ant-***tu-clave-secreta***"

# Verifica que funciona
claude -p "Hola, ¿funcionas?"
🔐 Seguridad: Nunca escribas tu API Key en archivos versionados (git) o .claude/settings.json. Usa variables de entorno o la autenticación OAuth.

1.3 — Comandos esenciales (slash commands)

Una vez dentro de Claude Code, los comandos comienzan con /. Escribe / para ver la lista completa con autocompletado.

1.4 — Navegación de archivos con @

Claude Code permite mencionar archivos y directorios directamente con el carácter @ dentro de un prompt — similar a un IDE moderno. 

> Lee @src/auth/login.ts y compáralo con @src/auth/register.ts.
  Identifica duplicación lógica y propón una refactorización
  a un módulo @src/auth/shared/validators.ts
📌 Buena práctica: Para proyectos grandes, crea un CLAUDE.md en la raíz con el stack, convenciones de código y estructura de carpetas. Claude lo lee automáticamente al iniciar cada sesión.
Niveles / Nivel 2

Nivel 2 Avanzado: MCP & Tokens

Conecta Claude Code a herramientas externas vía Model Context Protocol y aprende a gestionar tu ventana de contexto como un profesional.

2.1 — Model Context Protocol (MCP)

MCP es un estándar abierto creado por Anthropic que permite a Claude Code comunicarse con servicios externos (GitHub, Postgres, Slack, navegadores) vía servidores que exponen herramientas, recursos y prompts. Soporta tres transportes: stdio (local, baja latencia), SSE (remoto streaming) y HTTP. 

# Exporta tu token como variable de entorno (NO lo escribas en el JSON)
export GITHUB_TOKEN="ghp_tu_token_aqui"

# Registra el servidor MCP de GitHub (transporte stdio por defecto)
claude mcp add github -e GITHUB_TOKEN -- npx -y @modelcontextprotocol/server-github

# Verifica que esté conectado
claude mcp list
# Salida esperada:  github: connected (stdio)
# Servidor remoto SSE
claude mcp add --transport sse my-remote https://mi-servidor.com/mcp/sse

# Servidor remoto HTTP con headers de auth
claude mcp add --transport http composio-server "https://mcp.composio.dev/..." \
  --headers "X-API-Key:TU_API_KEY"

2.2 — Gestión de tokens y contexto

El recurso más caro en una sesión agéntica es la ventana de contexto. Estos comandos te permiten observar y reducir consumo:

2.3 — Memoria persistente con /memory

A diferencia de /compact que resume el historial actual, /memory guarda información de forma permanente que persiste entre sesiones. Perfecta para contexto del proyecto, decisiones arquitectónicas o información sensible que no quieres perder. 

# Sesión 1: Documentar la arquitectura
> /memory add "Stack: Next.js 14 + Prisma + PostgreSQL. DB en AWS RDS. Redis cache."

# Sesión 2 (después de cerrar): Claude recuerda automáticamente
> ¿Qué base de datos usamos?
Claude: Según tu memoria, usas PostgreSQL en AWS RDS con Redis de cache.

# Ver toda la memoria del proyecto
> /memory show

# Borrar una entrada
> /memory delete "Stack: ..."

2.4 — Configuración declarativa de MCP con .mcp.json

En lugar de ejecutar comandos claude mcp add manualmente, puedes declarar tus servidores MCP en un archivo .mcp.json en la raíz del proyecto. Claude Code lo cargará automáticamente al iniciar. 

{
  "mcpServers": [
    {
      "name": "github",
      "transport": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    },
    {
      "name": "postgres",
      "transport": "stdio",
      "command": "node",
      "args": ["./mcp-servers/postgres.js"],
      "env": {
        "DB_URL": "${DATABASE_URL}"
      }
    },
    {
      "name": "api-docs",
      "transport": "sse",
      "url": "https://mi-api.com/mcp/sse"
    }
  ]
}
💡 Tip: Versionea .mcp.json en git (sin secrets). Las variables ${...} se leen de variables de entorno en tiempo de ejecución.

2.5 — El comando /compact en profundidad

Cuando una sesión larga acumula miles de tokens (lecturas de archivos, salidas de comandos, iteraciones), /compact resume el historial preservando decisiones clave y código modificado, pero descartando ruido. 

# Antes de un cambio importante, mira tu uso de contexto
> /context

# Si superas ~70% de la ventana, compacta con un foco claro
> /compact mantén el plan de migración a TypeScript y los archivos
  ya refactorizados; descarta los logs de errores resueltos
⚠ Aviso de tokens MCP: Cada servidor MCP conectado añade descripciones de herramientas al contexto. Claude Code muestra una alerta cuando una salida MCP supera 10.000 tokens. Configura MAX_MCP_OUTPUT_TOKENS (por defecto 25.000) según tus necesidades.
Niveles / Nivel 3

Nivel 3 Experto: Skills & Automatización

Las Skills son la evolución de los antiguos slash commands: archivos SKILL.md que Claude puede invocar manualmente (/nombre-skill) o de forma autónoma cuando detecta el contexto.

3.0 — Comandos disponibles en Nivel 3

Los siguientes comandos están diseñados para automatización, orquestación y creación de Skills personalizadas:

3.1 — Anatomía de una Skill

Una Skill es simplemente un directorio con un SKILL.md:

~/.claude/skills/             # Personal (todos los proyectos)
└── security-audit/
    └── SKILL.md

.claude/skills/               # Proyecto (compartido en git)
└── code-review/
    ├── SKILL.md
    └── checklist.md          # archivos referenciados

3.2 — Crear tu primera Skill: /security-audit

---
name: security-audit
description: Audita el código en busca de vulnerabilidades comunes
  (SQLi, XSS, secretos expuestos, configuraciones inseguras). Úsalo
  cuando el usuario mencione seguridad, hardening o revisión de
  vulnerabilidades.
allowed-tools: Read, Grep, Glob, Bash(git diff:*)
model: claude-opus-4-7
---

# Auditoría de Seguridad

Analiza el código del proyecto buscando:

1. **Inyección SQL** — queries construidas por concatenación
2. **XSS** — output sin escapar en plantillas / DOM
3. **Secretos expuestos** — keys, tokens, contraseñas en código
4. **Configuraciones inseguras** — CORS abierto, debug=true, etc.
5. **Dependencias vulnerables** — revisa package.json / requirements

Para cada hallazgo, devuelve:
- Archivo y línea exacta
- Severidad (crítica / alta / media / baja)
- Código actual + parche recomendado
- Referencia OWASP cuando aplique

Una vez guardado, la Skill está disponible inmediatamente. Invócala con /security-audit o deja que Claude la dispare automáticamente cuando detecte intención coincidente con el campo description.

3.3 — Skill con argumentos dinámicos

---
name: fix-issue
description: Resuelve un issue de GitHub siguiendo nuestras convenciones
argument-hint: [issue-number] [priority]
allowed-tools: Read, Edit, Bash(gh:*), Bash(git:*)
---

Resuelve el issue #$1 con prioridad $2.

Pasos:
1. `gh issue view $1` para leer la descripción
2. Crear branch `fix/issue-$1`
3. Implementar cambios respetando convenciones de CLAUDE.md
4. Ejecutar tests relevantes
5. Crear commit + PR enlazado al issue

Uso: /fix-issue 247 high

3.3+ — Orquestación de sub-agentes

Claude Code puede crear y orquestar sub-agentes — instancias paralelas de Claude que trabajan en paralelo en diferentes tareas. Perfecto para:

  • Investigación + Implementación: Un agente revisa requisitos mientras otro implementa.
  • Revisión paralela: Un agente audita seguridad, otro revisa tests, otro style.
  • Pipelines de datos: Agentes en serie: fetch → transform → validate → upload.
---
name: parallel-refactor
description: Refactoriza el código en paralelo
allowed-tools: Read, Edit, Bash(git:*), Task
---

# Refactorización en paralelo

Con la herramienta Task, crea dos sub-agentes:

```
!`claude task --name investigar -- grep -r "deprecated_func" src/`
!`claude task --name implementar -- "Reemplaza todas las llamadas encontradas"`
```

Espera a que ambas terminen (ambos agentes reportan estado).
Luego revisa cambios y haz commit.
🚀 Escalabilidad: Los sub-agentes heredan el contexto (CLAUDE.md, archivo.md, archivos mencionados) pero ejecutan independientemente. Úsalos para paralelizar trabajo costoso en tokens o tiempo.

3.5 — Automatización con hooks

Los hooks ejecutan comandos shell en respuesta a eventos de Claude Code (PreToolUse, PostToolUse, etc.). Configurables en .claude/settings.json: 

{
  "model": "claude-sonnet-4-6",
  "permissions": {
    "allowedTools": ["Read", "Write", "Bash(git:*)", "Bash(npm:*)"],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Write(./production.config.*)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write(*.py)",
        "hooks": [{ "type": "command", "command": "ruff format $file" }]
      },
      {
        "matcher": "Write(*.ts)",
        "hooks": [{ "type": "command", "command": "prettier --write $file" }]
      }
    ]
  }
}
Producción / Seguridad

Seguridad & Hardening

Trabajar con un agente que tiene acceso a tu sistema de archivos requiere una postura defensiva. Estas son las prácticas mínimas que un perfil senior debe aplicar antes de poner Claude Code en un entorno con datos reales.

🛡 1. Prevenir fuga de archivos .env y secretos

El bloqueo se hace a nivel de permisos del agente, no solo del .gitignore. La directiva deny impide explícitamente que Claude lea o escriba sobre rutas sensibles, incluso si tú se lo pides. 

{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./**/secrets/**)",
      "Read(./**/*.pem)",
      "Read(./**/*.key)",
      "Read(./id_rsa)",
      "Write(./production.config.*)",
      "Bash(curl * | sh)",
      "Bash(rm -rf /*)"
    ]
  }
}

🛡 2. Archivo .claudeignore / patrones de exclusión

Además de los permisos, define patrones para que Claude ni siquiera indexe ciertos archivos al cargar el contexto del proyecto. Replica la sintaxis de .gitignore. 

# Secretos y credenciales
.env
.env.*
*.pem
*.key
id_rsa
**/secrets/**
**/credentials.json

# Datos sensibles
**/customer-data/**
**/*.sql.dump
**/backups/**

# Artefactos pesados (innecesarios para el contexto)
node_modules/
dist/
build/
.next/
coverage/
**/*.log

# Archivos personales
.DS_Store
.idea/
.vscode/settings.json

🛡 3. MCP: tokens vía variables de entorno

Nunca escribas tokens directamente en .mcp.json. Usa la flag -e al registrar el servidor — el token vive en tu shell, no en archivos versionados. 

# ❌ MAL: token literal en JSON (acaba en git)
# claude mcp add github --env "GITHUB_TOKEN=ghp_xxx" ...

# ✅ BIEN: variable de entorno por referencia
export GITHUB_TOKEN="ghp_..."
claude mcp add github -e GITHUB_TOKEN -- npx -y @modelcontextprotocol/server-github

🛡 4. Mitigar sesgos de seguridad en código generado

Los LLMs tienden a generar patrones inseguros si no se les corrige (ej. queries por concatenación, validación cliente-only, CORS abierto). Estrategias:

  • CLAUDE.md con reglas explícitas: «Toda query SQL DEBE usar parámetros preparados. Nunca SELECT * FROM x WHERE id = ${id}.»
  • Hook PostToolUse que ejecute un linter de seguridad (semgrep, bandit) tras cada Write.
  • Skill /security-audit obligatoria antes de mergear.
  • Principio de mínimo privilegio en allowedTools: no concedas Bash(*); lista comandos uno a uno.

🛡 5. Auditoría de servidores MCP de terceros

⚠ Crítico: Un servidor MCP es código que se ejecuta con tus permisos. Antes de instalar uno de la comunidad: revisa el repositorio, fija la versión exacta (@1.2.3, nunca @latest), y prefiere tokens de solo lectura cuando el caso de uso lo permita.
Producción / Casos de Uso

Casos de Uso Prácticos

Flujos reales que usamos en equipos profesionales, listos para copiar y adaptar a tu stack.

📦 Caso 1 — Refactorización de un módulo legacy

> Lee @src/legacy/UserManager.js (es código de 2018, jQuery + callbacks).

  Refactoriza siguiendo este plan:
  1. Convierte a TypeScript estricto (.ts)
  2. Reemplaza callbacks por async/await
  3. Extrae responsabilidades: separa persistencia (UserRepository),
     validación (UserValidator) y casos de uso (UserService)
  4. Añade tests Jest cubriendo los happy paths y 2 edge cases
     por método público
  5. NO cambies la firma pública del módulo: otros archivos lo
     importan y no quiero romperlos. Verifica con grep antes.

  Procede archivo por archivo y enséñame el diff antes de escribir.

📦 Caso 2 — Code Review de un PR

---
name: code-review
description: Revisión exhaustiva del último commit/PR
allowed-tools: Read, Grep, Bash(git diff:*), Bash(git log:*)
---

## Cambios a revisar
!`git diff --name-only HEAD~1`

## Diff completo
!`git diff HEAD~1`

## Checklist de revisión
Analiza los cambios de arriba contra:

1. **Calidad** — legibilidad, complejidad ciclomática, naming
2. **Seguridad** — inyecciones, secretos, validación de input
3. **Performance** — N+1, loops innecesarios, memoización
4. **Tests** — ¿cubre casos felices y de error?
5. **Documentación** — JSDoc/docstrings actualizados

Devuelve feedback agrupado por prioridad (🔴 bloqueante,
🟡 sugerencia, 🟢 nit) con líneas concretas.

📦 Caso 3 — Configuración recomendada para equipos

# Proyecto: Plataforma E-commerce

## Stack
- **Frontend**: Next.js 14 + TypeScript + Tailwind + Zustand
- **Backend**: Node.js 22 + Fastify + Prisma
- **DB**: PostgreSQL 16
- **Tests**: Vitest (unit), Playwright (e2e)

## Convenciones
- TypeScript estricto: NO usar `any`. Si dudas, usa `unknown` + type guards.
- Componentes funcionales con hooks. Sin clases.
- Imports absolutos desde `@/` (ya configurado en tsconfig).
- Tests al lado del código: `Foo.ts` → `Foo.test.ts`.

## Arquitectura
- /src/app          → rutas Next.js
- /src/components   → UI reutilizable
- /src/features/*   → módulos de dominio (auth, cart, checkout, ...)
- /src/lib          → utilidades transversales
- /src/server       → API Fastify, repos Prisma

## Reglas de seguridad
- TODA query a DB usa Prisma (no SQL crudo).
- TODO endpoint valida input con Zod.
- NUNCA logear PII (emails, nombres, IPs).

## Comandos útiles
- `npm run dev` — desarrollo
- `npm run test` — tests
- `npm run lint` — eslint + prettier --check

📦 Caso 4 — Generar tests para código existente

> Para @src/features/checkout/calculatePrice.ts genera un suite Vitest
  que cubra:
  - Caso base (1 producto, sin descuento, sin impuestos)
  - Cupones: porcentaje, monto fijo, cupón inválido
  - Múltiples ítems con cantidades
  - Edge: carrito vacío, precios negativos (debe lanzar)
  - Tax inclusive vs exclusive

  Usa describe/it anidados, mockea solo lo estrictamente externo
  (servicio de impuestos), y apunta a >90% de cobertura de líneas.

📦 Caso 5 — Migración asistida (JS → TS)

> Voy a migrar /src/utils a TypeScript. Hagamos esto:

  1. Listas todos los .js de @src/utils
  2. Para cada archivo:
     a. Lee el código y los tests existentes
     b. Crea la versión .ts con tipos estrictos inferidos del uso
     c. Añade JSDoc/typedefs donde falten
     d. Renombra .js → .ts y actualiza imports en todo el repo
     e. Corre `npm run typecheck` para verificar
  3. Después de los 5 primeros archivos, hacemos /compact y seguimos.

📦 Caso 6 — Investigar un bug en producción

> Tenemos un bug intermitente: "RangeError: Invalid time value"
  en producción. Stack trace apunta a @src/lib/dates/format.ts:42.

  Plan:
  1. Lee el archivo y entiende qué hace la línea 42
  2. Busca con grep todos los call sites en el repo
  3. Identifica qué inputs podrían producir un Date inválido
  4. Propón fix defensivo (validación + fallback)
  5. Añade un test que reproduzca el bug ANTES del fix
     (debe fallar) y luego pase con el fix aplicado
